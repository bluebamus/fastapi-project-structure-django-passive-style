1. 이 안내서의 범위와 개발 기준

이 문서는 이 저장소(fastapi-project-structure-django-passive-style)의 2026-09-17 작업 트리 기준 신규 API View·DB 테이블 개발 지침이다. 기동 환경은 서버 수명주기 안내서와 분리하고 여기서는 실제 catalog와 reports를 따라 데이터·호출·트랜잭션 경계를 설명한다. 별도 DI container나 추상 interface를 새로 도입하는 안내가 아니라 기존 클래스·함수를 재사용하는 절차이다.

기본 경로: 입력 Schema → View/Router → 주입된 Service → Repository → AsyncSession → DB. 응답은 ORM 객체 또는 Raw 결과를 Pydantic DTO로 검증해 HTTP 계약으로 내보낸다.

“뷰”는 이 저장소에서 API endpoint 함수의 HTTP 역할을 주로 뜻한다. 전통적 HTML template View, SQLAdmin ModelView, DB의 SQL VIEW는 서로 다른 개념이다. 아래 MVC 매핑은 프로젝트를 이해하기 위한 대응이지 FastAPI가 MVC 폴더를 강제한다는 뜻이 아니다. 새 inventory 코드는 교육용 제안이며 현재 앱에 구현된 기능으로 표시하지 않는다.

Repository 패턴은 SQL 변경을 View에서 분리하고, Service Layer는 동일 업무를 API·background·Celery에서 재사용할 지점을 제공한다. 생성자 주입은 Service(session)처럼 실제 필요한 객체를 전달하는 방식이다. 공통 필드는 작은 Mixin을 조합한다. registry core와 FastAPI·SQLAdmin 결선 adapter 분리는 프레임워크 경계를 분리하는 Adapter 구조이다.

별도 UnitOfWork 클래스는 없다. 현재 트랜잭션 상태는 AsyncSession이 갖고, 요청 commit 경계는 쓰기 handler 본문이다. 새 UnitOfWork·Factory·Strategy를 요구가 없는데 추가하지 않는다. ORM과 Raw는 같은 업무 경계를 따르지만(tests/test_orm_raw_parity.py) 두 Base는 상속 관계가 없고 public method 이름·결과 타입도 다르다(ARCHITECTURE §4.6).

3. 기존 테이블은 어떻게 등록·사용되는가

모델 class 정의가 import되면 SQLAlchemy declarative 매핑을 통해 Base.metadata에 Table 정보가 등록된다. 이것은 DB 서버에 테이블이 이미 생성됐다는 뜻이 아니다. 개발 DDL 또는 Alembic이 별도 생성/변경 작업을 한다. Schema 모델을 작성하는 것만으로 metadata·DB 테이블이 생기지 않는다.

기능모델테이블역할
homeapp/features/home/models/models.py · UserAccessLoguser_access_logs접속 로그 / background sink
blogapp/features/blog/models/models.py · Postblog_posts게시글 CRUD
replyapp/features/reply/models/models.py · Replyreplies댓글 CRUD
snsapp/features/sns/models/models.py · SnsPostsns_postsSNS 게시물 CRUD
userapp/features/user/models/models.py · Userusers사용자·인증용 데이터
catalogapp/features/catalog/models/models.py · Productcatalog_productsORM 참조 예제
reportsapp/features/reports/models/models.py · SalesOrdersales_ordersRaw 일별 매출 원본

auth는 인증 endpoint를 제공하지만 독립 models/models.py 테이블이 없는 기능이다. 기능·router·모델은 1:1 필수 관계가 아니다. 예제 모델 사이에 이름이 비슷한 user_id/customer 등이 있더라도 선언되지 않은 FK·ORM relationship을 추정해서 만들지 않는다.

설치 모델은 AppConfig.import_models가 models 패키지에 공개된 매핑 class를 수집한다. models/__init__.py의 재노출을 빼먹으면 소유 테이블 수집에 빠질 수 있다. runtime create_all은 owned_tables를 명시한다.

전역 metadata는 이미 import된 class를 유지하므로 같은 Python 프로세스의 테스트·실험 모델이 섞일 수 있다. 앱 제거는 router뿐 아니라 테이블·데이터·migration 소유권까지 검토한다. 앱 미설치가 기존 DB 테이블을 자동 삭제하는 동작은 아니다.

4. Product 모델·Schema·기본값·제약

Product는 catalog_products에 매핑되고 문자열 UUID id와 created_at/updated_at을 공통 Mixin에서 받는다. Base·UUIDPrimaryKeyMixin·TimestampMixin을 조합한다. sku는 unique이며 name/description/price/stock/is_active를 갖는다. 금액은 Numeric(12,2)와 Decimal로 다룬다.

UUID·시간 default는 class import 때 모든 행에 한 번 채우는 값이 아니라 행 INSERT 시 적용되는 Python 기본 생성 함수이다. UpdatedAtMixin.onupdate는 ORM/Core가 발행하는 UPDATE에 적용되며 Raw SQL이 이를 자동 호출하지 않는다. Raw INSERT/UPDATE는 필요한 PK·시간·default를 SQL 바인딩 또는 DB server_default로 직접 다뤄야 한다.

DB nullable/unique/type/index와 Pydantic min_length/price 범위는 목적이 다르다. API 입력은 schema에서 검증하고 동시성 상황의 최종 무결성은 DB 제약으로 보호한다. 현재 API price는 ge=0이고 sku는 생성 요청의 필수 필드이다. stock도 ge=0이다. DB Numeric 선언 자체가 같은 양수/재고 규칙을 전부 강제하는 것은 아니다.

응답 ProductResponse의 from_attributes=True는 ORM 속성에서 읽는 설정이다. 현재 ProductResponse는 created_at/updated_at도 포함한다. 모델.to_dict를 바로 공개하면 해시·내부 컬럼까지 유출할 수 있으므로 응답 필드를 Schema로 정한다.

선택적인 PATCH 필드의 None은 “미전달”과 다르다. exclude_unset=True는 안 보낸 필드만 제외하므로 명시 null은 남는다. 현재 ProductUpdate의 일부 non-nullable 필드도 None을 허용할 수 있으므로 새 기능은 null 허용·거부 정책을 명확히 정하고 테스트한다.

5. 기본 API View와 prefix의 실제 합성

최하위 products.py는 APIRouter와 endpoint 함수를 선언한다. 상위 catalog/api/routers/router.py의 catalog_router가 prefix="/v1/catalog"로 포함하고, registry/adapter가 catalog_router를 prefix="/api"에 포함한다. 따라서 파일 내부 "/products"의 최종 URL은 /api/v1/catalog/products이다.

method최종 경로현재 함수·세션
POST/api/v1/catalog/productscreate_product / get_catalog_service / writer
GET/api/v1/catalog/productslist_products / get_catalog_service_readonly
GET/api/v1/catalog/products/{product_id}get_product / readonly
PATCH/api/v1/catalog/products/{product_id}update_product / writer
DELETE/api/v1/catalog/products/{product_id}delete_product / writer
GET/api/v1/reports/daily-salesget_daily_sales_report / readonly

View는 HTTP parameter/body를 Pydantic으로 받아 Service를 호출한다. Query의 skip >= 0, 1 <= limit <= 100은 범위 방어선이다. Path가 UUID라고 설명돼도 실제 타입이 str이면 문자열 UUID 형식을 자동 엄격 검증하는 것은 아니다. 신규 경로는 필요할 때 UUID 타입이나 별도 검증을 명시한다.

OpenAPI operation_id는 앱 전체에서 유일하게 하고 summary/description/tags/response_model/responses를 실제 반환 계약과 맞춘다. API_VERSION 설정은 선언만 있고 소비처가 없다. 버전 prefix는 각 기능 router.py의 /v1 선언이 정하므로 config 값을 바꿔도 URL은 바뀌지 않는다. 공개 경로 전체(22 경로 / 37 오퍼레이션)는 README API 표와 tests/test_route_inventory.py가 고정한다.

6. 상품 생성 한 요청의 클래스·함수 추적

get_catalog_service는 get_writer_db_session을 Depends로 받아 CatalogService(session)를 반환한다. Service 생성자는 BaseService에 세션을 보관하고 동일 세션으로 ProductRepository를 만든다. create_product는 입력을 model_dump해 Repository.create로 전달한다. Repository는 Product 인스턴스를 생성하고 CRUDBase._add가 session.add → await flush → await refresh를 수행한다. flush는 INSERT를 보내 기본값·제약을 확인하지만 아직 commit은 아니다.

현재 create_product의 핵심 순서 — 이 저장소의 모든 쓰기 핸들러가 같은 순서다

product = await service.create_product(payload)
response = ProductResponse.model_validate(product)  # 검증 실패면 커밋하지 않는다
await service.commit()
return response

모든 쓰기 핸들러(생성·수정)는 응답 DTO 검증 → commit → 응답 한 가지 순서를 따른다(DEVELOPMENT §4.2). 반대 순서면 DTO 검증 실패가 500을 내는데 데이터는 이미 커밋돼 남는다. tests/test_validate_before_commit.py가 전 기능에서 DTO 검증을 실패시켜 500·커밋 0회·DB 불변을 확인한다. commit을 dependency yield 이후(teardown)에 두지 않으며, DTO가 읽을 필드는 Repository에서 명시적으로 로드한다.

DB commit과 HTTP 전송은 하나의 원자적 트랜잭션이 아니다. commit 성공 후 연결 단절·응답 직렬화 실패가 생길 수 있다. 중요한 생성 업무는 idempotency 키·중복 처리 정책을 요구사항으로 정한다. “클라이언트가 2xx를 못 받았으니 저장 안 됨”으로 단정하지 않는다.

공개 메서드는 위 8개로 고정돼 있다(ADR-016, tests/core/test_repository_base.py). 공통 계층이 모든 domain 조회·eager loading·정렬을 해결한다고 확대하지 않는다 — 그런 쿼리는 기능 Repository에 명시적 메서드로 둔다.

CatalogService가 get_product·delete_product의 부재를 ProductNotFoundException으로 변환한다. active_only=true이면 ProductRepository.get_active()가 판매 중 상품만 SKU 오름차순으로 돌려주고, active_only=false이면 정렬 없는 get_all을 쓴다. total은 필터와 무관한 count() 전체 상품 수다. OpenAPI 설명(listProducts)도 이 동작을 그대로 적는다.

신규 pagination은 고정 정렬과 동률 PK를 명시하고 같은 필터로 count를 계산한다. 빈 PATCH/no-op, 동일값 UPDATE의 rowcount=0, 동시 삭제·갱신은 별도 시나리오로 검사한다. 상태 전환·재고 차감은 무조건 조회 후 UPDATE만으로 안전하지 않으며 조건부 UPDATE·잠금·제약 등 실제 동시성 정책을 설계한다.

도메인 SQL은 ProductRepository의 명시적 메서드로 추가한다. 잘못된 문자열 컬럼명에 의존하는 범용 filter를 늘리기보다 SQLAlchemy 모델 속성을 사용한다. 반환이 Sequence[Product]인지 DTO projection인지 책임 경계를 명확히 한다.

8. 주입·재사용·read-only/writer 선택

실제 dependency 구조

async def get_catalog_service(
    session: AsyncSession = Depends(get_writer_db_session),
) -> CatalogService:
    return CatalogService(session)

async def get_catalog_service_readonly(
    session: AsyncSession = Depends(get_read_only_db_session),
) -> CatalogService:
    return CatalogService(session)

FastAPI가 dependency 그래프를 풀어 세션을 생성하고 반환한 Service를 endpoint parameter에 넣는다. 타입 annotation만으로 Service를 자동 생성하는 것이 아니라 Depends에 지정한 callable이 객체 조립을 수행한다. 일반 Service/Repository는 FastAPI를 모르는 생성자 주입으로도 실행할 수 있어 background·테스트에서 재사용 가능하다.

같은 요청의 같은 dependency는 기본 use_cache=True로 재사용된다. writer getter와 read-only getter는 다른 callable이므로 무조건 동일 세션은 아니다. 서로 다른 Service가 하나의 원자적 쓰기에 참여해야 한다면 같은 writer session을 주입하고 그 요청의 commit 주체는 하나로 둔다. Service 자체를 전역 싱글턴으로 두면 보관한 session이 요청을 넘나들 수 있으므로 금지한다.

DB_ROUTER_ENABLED와 DB_REPLICATION_ENABLED가 모두 활성일 때 reader 분산을 고려한다. replica가 없거나 복제가 꺼졌으면 읽기도 writer로 간다. 쓰기 이후 sticky는 세션 내부 정책이며 새 요청의 read-only session까지 복제 지연을 없애지 않는다.

read-only session의 ORM 쓰기 차단(ReadOnlyRoutingError)은 RoutingSession.get_bind에 있으므로 DB_ROUTER_ENABLED=true일 때만 동작한다. 기본값(false)에서는 read-only getter로 받은 세션에서도 ORM 쓰기가 막히지 않으므로 조회 경로에서 쓰기 메서드를 부르지 않는 규칙을 코드와 tests/test_read_path_no_commit.py로 지킨다. Raw primitive(RawCRUDBase)는 read_intent/write_intent execution option을 붙이고, router 설정과 무관하게 is_read_only_session으로 Raw 쓰기를 read-only session에서 실행 전 거부한다. 미표시 TextClause는 router에서 write로 취급하는 fail-closed 정책이다. 이 보호가 임의 코드의 session.execute까지 완전 SQL 의미 검증하는 sandbox인 것은 아니다.

읽기 전용 표시·session.info는 DB 권한을 대체하는 보안 장치가 아니다. 개발 경계와 운영의 read-only 계정·권한을 함께 설계한다. DI 공식 문서.

9. 비동기 트랜잭션·오류·응답 경계

flush는 현재 트랜잭션 내부에 SQL을 내보내고 refresh는 DB 값을 다시 읽는다. commit은 전체 변경을 확정한다. Repository 또는 여러 Service 중간에서 commit하면 이후 실패가 앞 변경을 rollback하지 못한다. 기존 구조대로 요청의 쓰기 handler 본문에서 한 번 commit한다. 조회 dependency는 commit하지 않는다.

yield dependency는 현재 기본 request scope에서 응답 후 teardown된다. scope="function"은 응답 전 종료로 선택할 수 있으므로 “모든 FastAPI yield 정리는 언제나 응답 후”라고 일반화하지 않는다. 이 프로젝트는 기본 dependency 경계를 사용하며 commit을 teardown에 맡기지 않는다. FastAPI scope 공식 근거.

DB 오류는 SQLAlchemyError·IntegrityError 등으로 발생할 수 있고 기존 Base/기능별 변환 범위가 서로 다르다. Repository의 create 변환이 commit 단계 오류까지 자동 포함하는 것은 아니다. BaseService.commit은 커밋 시점의 SQLAlchemyError도 convert_db_error로 변환한다. 사용자 응답에는 SQL·bind 값·DSN·secret을 넣지 않는다.

전달된 예외에서 session generator는 예외를 그대로 재전파하고 async with의 close가 활성 트랜잭션 rollback과 세션 정리를 담당한다. 이미 commit한 뒤 실패했다면 rollback이 저장을 되돌리지 않는다. 취소는 BaseException 계열이라 일반 except Exception과 다르므로 취소·timeout 테스트가 필요하다.

쓰기 경로의 형태 — 모든 기존 핸들러와 같은 순서. route decorator·metadata는 기존 예제에 맞춰 추가

async def create_product(payload: ProductCreate, service: CatalogService = Depends(get_catalog_service)):
    product = await service.create_product(payload)
    response = ProductResponse.model_validate(product)
    await service.commit()
    return response

10. ORM과 Raw 선택: reports의 실제 처리

일반 단건 CRUD·관계 조회는 ORM을 기본값으로 한다. 실제 집계·대량 집합 연산·측정한 실행 계획 때문에 Raw가 필요한 경우만 기능 RawRepository를 둔다. Raw는 “항상 빠름”이나 “Schema/Service 불필요”를 뜻하지 않는다.

현재 /api/v1/reports/daily-sales는 View → daily_sales_report() → SalesReportRawRepository.daily_sales → RawRepositoryBase.fetch_all → RowMapping → Pydantic DTO로 이어진다. 계산 결과는 원본 테이블 한 행이 아니므로 일별 DTO를 영속 ORM class처럼 만들 필요가 없다. 원본 sales_orders는 프로젝트 소유 테이블이므로 모델·migration이 존재한다.

reports는 ordered_at 기준으로 paid 상태만 집계한다. Service가 기간(종료 ≥ 시작, 최대 366일)을 검증하고 end_exclusive(= end_date + 1일)를 계산한다. Repository는 daily_sales(fetch_all)와 order_count(fetch_scalar) 두 쿼리를 수행하고, Service는 RowMapping을 DTO로 검증해 report envelope를 반환한다. 조회 전용이라 commit하지 않으며 집계 결과를 저장하는 기능은 없다.

Raw 공개 메서드결과/책임
fetch_one첫 RowMapping 또는 None. 읽기 의도(for_update=True면 쓰기)
fetch_allRowMapping 목록. 읽기 의도(for_update=True면 쓰기)
fetch_scalar첫 행 첫 컬럼 또는 None. 실제 query별 타입 검증 필요
execute영향 행 수 int(존재 판단에 쓰지 않음). 항상 쓰기 의도, commit 없음

값은 named bind parameter로 전달한다. 테이블·컬럼·ASC/DESC 같은 식별자는 bind 값으로 대체되지 않으므로 동적 요청값 보간을 하지 않는다. 필요한 정렬은 코드 소유 고정 SQL 또는 기존 식별자 검증 규약을 쓴다. query_name은 sales_report.daily_sales 같은 안정적 코드 상수(feature.use_case, 소문자·숫자·밑줄, 점 하나, 64자 이하)이다. validate_query_name이 실행 전에 검사하고 어기면 InvalidQueryNameError다. 전체 규칙은 DEVELOPMENT §3에 있다.

Raw DML은 ORM Mixin의 Python default/onupdate를 우회할 수 있다. 필요 컬럼을 명시하고 DB 반환 타입의 Decimal·날짜를 DTO에서 확인한다. SQL 안전 검사·테스트 통과는 DB 권한·대상 방언·실행 계획까지 대신하지 않는다.

12. 작은 신규 기능 예시: 기존 기반을 재사용

신규 models/models.py 예시

from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column
from app.core.models.models_base import Base, UUIDPrimaryKeyMixin, TimestampMixin

class Item(Base, UUIDPrimaryKeyMixin, TimestampMixin):
    __tablename__ = "inventory_items"
    name: Mapped[str] = mapped_column(String(200), nullable=False)

신규 schemas/item_schema.py 예시 — 시간·내부 필드는 필요할 때만 공개

from pydantic import BaseModel, ConfigDict, Field

class ItemCreate(BaseModel):
    name: str = Field(min_length=1, max_length=200, description="품목명")

class ItemResponse(ItemCreate):
    model_config = ConfigDict(from_attributes=True)
    id: str

신규 Repository/Service 배선 예시 — 실제 파일에서는 AsyncSession·입력/반환 타입 annotation을 추가

from app.core.repositories.repository_base import BaseRepository
from app.core.services.services_base import BaseService
from app.features.inventory.models.models import Item

class ItemRepository(BaseRepository[Item]):
    model = Item

class InventoryService(BaseService):
    def __init__(self, session): 
        super().__init__(session)
        self.repository = ItemRepository(session)

    async def create_item(self, payload):
        return await self.repository.create(payload.model_dump())

신규 Dependency/View 핵심 예시 — 여기서의 endpoint는 현재 저장소에 존재하지 않음

from fastapi import APIRouter, Depends
from sqlalchemy.ext.asyncio import AsyncSession
from app.core.db.session import get_writer_db_session
# 새 Service·Schema를 위 실제 제안 모듈에서 import

async def get_inventory_service(
    session: AsyncSession = Depends(get_writer_db_session),
) -> InventoryService:
    return InventoryService(session)

router = APIRouter()

@router.post("/items", response_model=ItemResponse, status_code=201,
             summary="품목 생성", description="새 품목을 생성합니다.",
             operation_id="createInventoryItem")
async def create_item(payload: ItemCreate,
                      service: InventoryService = Depends(get_inventory_service)) -> ItemResponse:
    item = await service.create_item(payload)
    response = ItemResponse.model_validate(item)
    await service.commit()
    return response

13. 테이블 생성·변경·SQL VIEW의 관리 절차

개발 DB에서 실행할 명령 예시 — 이 작업에서는 migration을 생성·적용하지 않음

uv run alembic revision --autogenerate -m "add inventory items"
# 생성된 migration의 upgrade/downgrade·drop·nullable·데이터 이동 검토
uv run alembic upgrade head
uv run alembic current
uv run alembic heads

migrations/env.py는 db_settings.ALEMBIC_URL로 writer 동기 URL을 선택한다. 신규 model 등록 후 candidate를 생성하고 실제 upgrade/downgrade·인덱스·FK·default·기존 데이터 영향을 검토한다. rename을 자동 감지한다고 가정하지 않는다. Alembic 공식 문서도 생성 후보의 수동 검토를 요구한다.

이미 create_all로 만든 개발 DB와 초기 migration을 섞는 전환은 실제 revision 체인(ARCHITECTURE §10)에 맞춘다. 실데이터가 있는 DB에서 무조건 drop/recreate·stamp head를 실행하지 않는다. stamp는 테이블을 만들지 않으며 검증 없이 이력만 맞추면 schema drift를 숨긴다.

현재 reports는 SELECT 집계이며 DB SQL VIEW 객체를 생성하는 기능은 아니다. SQL VIEW가 실제 필요한 경우 방언에 맞는 CREATE/DROP VIEW를 명시 migration으로 관리하고 Repository는 읽기 SQL·DTO 계약을 소유한다. 일반 Table 모델만으로 Alembic이 VIEW 정의 변경을 자동 추적한다고 가정하지 않는다. 별도 설계 예시이지 현재 구현 아니다.

다중 worker가 DEBUG=true로 동시에 개발 DDL을 수행할 수 있으므로 운영에서는 별도 migration 실행 주체를 두고 DEBUG=false를 명시한다. schema 확장→코드 전환→구 컬럼 제거 같은 호환 배포는 데이터·동시 운영 요구가 있을 때 계획한다.

14. 비동기·background·Celery 개발 원칙

async def는 await 가능한 I/O를 기다리는 동안 다른 요청이 진행할 수 있게 한다. CPU 연산이 자동 병렬화되거나 동기 SDK 호출이 자동 비동기화되는 것은 아니다. async endpoint에서 time.sleep·동기 HTTP·파일 처리·큰 CPU 루프를 직접 돌리면 event loop를 막을 수 있다. 필요한 blocking I/O는 적절한 thread 경계, 무거운 CPU/내구 작업은 worker 정책을 검토한다. FastAPI async 공식 설명.

동일 AsyncSession으로 asyncio.gather를 실행하지 않는다. 한 트랜잭션의 여러 SQL은 순차 await하고 독립 병렬 작업은 작업별 session을 쓴다. 같은 엔진 pool도 다른 event loop에서 이미 생성된 연결을 임의 재사용하지 않는다. SQLAlchemy AsyncSession 공식 근거.

응답 Schema가 접근할 관계/컬럼은 Repository에서 selectinload 등 명시 로딩으로 준비한다. lazy relationship/deferred/expired 속성이 DTO 검증 중 암묵 I/O를 발생시키지 않도록 한다. 현재 공통 모델이 AsyncAttrs를 제공한다고 가정하지 않는다. expire_on_commit=False가 모든 relationship 로딩 문제를 해결하지 않는다.

요청 밖 작업 제안 — SomeService/do_write는 설명용 placeholder, 실제 import·업무 구현 필요

async with background_session() as session:
    service = SomeService(session)
    await service.do_write()
    await session.commit()

FastAPI Depends는 일반 coroutine을 직접 부른다고 자동 해결되지 않는다. 요청 밖에서는 위처럼 자원 context를 열고 Service를 직접 조립한다. 요청의 살아 있는 session·Service·Request를 Celery payload로 넘기지 말고 JSON 직렬화 가능한 id·값만 넘긴다. task는 자기 session을 열고 실패/재시도·중복 정책을 정의한다.

현재 access_log_tasks runner는 비핵심 로그를 드롭할 수 있다. 중요한 업무의 내구 큐가 아니다. Celery도 단순 전송만으로 정확히 한 번 처리를 보장하지 않으며 재시도·중복·DB commit과 enqueue 사이의 실패를 테스트한다. outbox 등 추가 구조는 실제 일관성 요구가 있을 때 선택한다.

새 공유 Redis 사용은 app.state.redis의 lifecycle 상태를 확인하는 작은 Depends accessor로 제공할 수 있지만 현재 공통 Redis dependency가 모든 기능에 자동 주입되어 있지는 않다. Redis 장애는 handler/runtime 오류 계약을 별도로 정한다.

15. 권한·테스트·관리·완료 기준

catalog/reports 예제에 endpoint가 있다고 현재 모든 CRUD에 사용자 권한 보호가 붙어 있다고 가정하지 않는다. JWT 발급/검증은 기존 auth feature와 utils/authenticator를 확인하고 새 endpoint에 필요한 인증·소유권·역할 검사를 명시한다. 인증 성공과 해당 데이터 수정 권한은 별개이다. SQLAdmin은 무인증이므로 운영 비활성/프록시 제한을 별도 관리한다.

기존 테스트는 tests와 feature별 tests에서 test_*.py 규약을 사용한다. endpoint 단위 테스트는 dependency_overrides로 Service/세션을 대체하거나 기존 fixture 패턴을 따른다. overrides는 테스트 종료 시 복원한다. lifespan을 검증할 때는 client context 또는 app.router.lifespan_context처럼 실제 context 진입을 수행한다. ASGITransport 요청만으로 startup이 자동 검증됐다고 가정하지 않는다.

전체 pytest에는 별도 MySQL/브라우저/Redis 준비가 필요한 범위가 포함된다. -m mysql은 compose.test.yaml의 MySQL 8.4(127.0.0.1:3309, 포트는 MYSQL_TEST_PORT)가 없으면 skip되고, -m browser는 실제 uvicorn을 띄우므로 Chromium·MySQL·Redis가 없으면 skip 없이 실패한다. 한 번에 돌리려면 uv run python -m scripts.review_gate(MySQL·브라우저 단계 제외는 --fast)를 쓴다. 16. 개발 작업 순서 요약과 문서 유지

  • 새 endpoint·테이블이 필요한지 확인하고 현재 feature 확장으로 해결되면 그 안에서 작업한다.
  • HTTP 계약·데이터 소유·권한·read-only/writer·동시성·실패 응답을 먼저 정한다.
  • 모델/Mixin·Schema·Repository·Service·Dependency·View를 기존 방식대로 작성한다.
  • config.INSTALLED_APPS 설치·models 재노출·router prefix·app/core/tags_metadata.py 태그·operation_id·Admin을 연결한다.
  • 모델 등록 후 migration 후보를 생성·검토하고 개발 DB에서 변경 전후를 확인한다.
  • DTO 검증/필드 로딩·응답 전 commit·rollback·취소·background session 경계를 점검한다.
  • 단위·endpoint·등록·트랜잭션·대상 MySQL 테스트와 lint/type 검사를 수행한다.
  • 기동 Redis·DB readiness·운영 DEBUG/ADMIN/secret/CORS를 확인하고 관련 문서를 함께 갱신한다.

현재 동작은 소스가 기준이며 ARCHITECTURE(동작 레퍼런스)·DEVELOPMENT(절차·규칙·체크리스트)와 함께 읽는다. 문서끼리 어긋나면 코드를 확인한 뒤 고친다. CRP 문서는 리뷰 상태·결정·잔여 위험 이력이지 runtime 등록 파일이 아니다. 이 안내서의 제안 예제는 새 기능을 실제 구현·실행했다는 증거가 아니며 모든 운영·동시성 시나리오를 검증했다는 의미도 아니다.
