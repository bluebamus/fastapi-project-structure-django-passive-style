5. 로깅

설정 단일 지점은 app/utils/logs/config.py 의 build_dictconfig() 이고, 첫 get_logger() 호출이 configure_logging() 으로 한 번 적용한다(ADR-019).

ENV 핸들러 시각
development console (밀리초) 로컬 타임존
test console 로컬 타임존
staging / production console + 날짜·크기 회전 파일 2개(LOG_FILE_ENABLED=true 일 때) UTC

모든 실행 경로가 이 구성 하나를 쓴다(logging-overhaul ADR-001) — 앱 로거, python main.py(setup_uvicorn_logging() 은 build_dictconfig() 를 그대로 돌려준다), uvicorn main:app·fastapi dev CLI(uvicorn 이 자기 구성을 건 뒤 앱 import 의 configure_logging() 이 다시 건다), Celery 워커·beat(setup_logging 시그널 수신자 app/celery/app.py 의 use_app_logging). uvicorn·uvicorn.error·uvicorn.access 로거는 자기 핸들러 없이 root 로 전파되므로 서버 줄·접속 줄이 앱 콘솔·파일에 같은 형식으로 나온다. 접속 줄의 요청 라인(client - "GET /p HTTP/1.1" 200)은 uvicorn 이 넘기는 메시지 그대로다. --no-access-log 은 유지된다. 예외: --reload(fastapi dev) 의 감시 프로세스는 앱을 import 하지 않아 Will watch for changes·Started reloader process 같은 몇 줄이 uvicorn 기본 형식으로 남는다(요청을 받는 자식 프로세스는 프로젝트 형식).

console 은 LOG_CONSOLE_ENABLED=true(기본)일 때만 붙는다(app/utils/logs/config.py 의 console_enabled()). 콘솔도 파일도 없으면 root 에 NullHandler 를 달아 logging.lastResort 가 stderr 로 새지 않게 하고, configure_logging() 이 stderr 에 경고 한 줄을 남긴다. Celery --loglevel 은 워커 root 레벨로 따르고, --logfile 을 주면 그 파일에도 같은 형식(LOG_FILE_FORMAT)으로 쓴다.

  • 파일(staging/production 에서만, LOG_DIR 아래 고정 이름) — 프로세스 종류는 app/utils/logs/setup.py 의 entry_process() 한 곳이 정한다 (진입 명령이 celery 면 워커 또는 beat, 아니면 웹. Celery 수신자는 entry_process(default="celery")).
프로세스 일반(LOG_FILE_LEVEL 이상) 에러(ERROR 이상)
웹(앱·uvicorn) app.log error.log
Celery 워커 celery.log celery-error.log
Celery beat celery-beat.log celery-beat-error.log

웹과 워커가 한 error.log 를 함께 쓰면 두 프로세스가 같은 파일을 회전시켜 깨진다 — 그래서 에러 파일도 프로세스별이다(ADR-003). 기동 초기 줄도 파일에 남는다: 설정 로드 직후 첫 get_logger() 가 진입 명령으로 프로세스 종류를 정하고 파일 핸들러까지 붙인다 — import 중에 나는 줄(예: [database] 라우팅 구성)이 콘솔에만 있고 파일에서 빠지지 않는다. 웹·python main.py·uvicorn main:app· 워커·beat 모두 같고, 핸들러는 한 번만 붙는다(tests/utils/test_log_early_lines.py, e2e L6 이 실제 프로세스로 대조한다 — integration-e2e ADR-011). - 회전·보관 — app/utils/logs/handlers.py 의 DailySizeRotatingFileHandler(표준 TimedRotatingFileHandler 상속). 매일 자정(UTC — 파일은 UTC 를 쓰는 staging/production 에만 있다)에 app.log → app.log.2026-10-19, 하루 안에서 LOG_MAX_SIZE_MB 를 넘으면 app.log.2026-10-19.1·.2…. 회전할 때마다 LOG_RETENTION_DAYS(기본 30, 0 = 지우지 않음)보다 오래된 날짜·분할 파일을 지운다 (정확히 N일 전 파일은 남는다). 파일 I/O 는 호출 흐름에서 동기 수행된다. - 여러 프로세스 주의 — 한 파일은 한 프로세스만 회전시킬 수 있다. uvicorn --workers 2 이상·Celery prefork(--concurrency > 1 의 자식 프로세스)는 같은 파일을 여러 프로세스가 회전시켜 안전하지 않다. 그 배포는 콘솔(stdout) + 수집기/logrotate, 파일 로그 끔 (LOG_FILE_ENABLED=false)으로 운영한다. 기동 시 감지하지는 않는다(워커 수를 앱이 믿을 만하게 알 방법이 없다 — 문서로만 안내). - 헤더(app=) — filters._app_from_path() 한 함수가 정한다. 우리 코드는 소스 경로(<기능명>·core·celery·utils·migrations·app), 저장소 밖 코드는 로거 이름 표(celery.*·kombu.* → celery, uvicorn.* → uvicorn, sqlalchemy.* → sqlalchemy, alembic.* → alembic, 그 밖 → ext). 새 기능은 아무것도 하지 않아도 자기 이름의 헤더가 붙는다. - 앱별 레벨 — LOG_APP_LEVELS="blog=DEBUG,sqlalchemy=WARNING". 키는 헤더 이름, 지정 없는 헤더는 LOG_LEVEL. 구현은 필터 하나 (AppLevelFilter, 모든 핸들러에서 ContextFilter 바로 뒤)이고 root 레벨은 전체 최솟값으로 내려 레코드가 필터까지 오게 한다. 형식·레벨이 틀리면 설정 로드가 실패하고, 모르는 헤더는 WARNING 한 줄만 남긴다. 핸들러는 여전히 root 에만 붙는다(앱별 로거 등록 없음, ADR-019). - 포맷: console 은 LOG_CONSOLE_FORMAT, 파일은 LOG_FILE_FORMAT, 시각은 LOG_DATE_FORMAT(development 는 뒤에 .밀리초). 기본값은 [{asctime} {tzname}] {levelname:5} [app={appname}] [{module}:{classname}:{funcName}:{lineno}] {message} / %Y-%m-%d %H:%M:%S (config.DEFAULT_LOG_FORMAT = app.utils.logs.LOG_FORMAT). 설정 로드 때 샘플 레코드로 한 번 렌더해 모르는 필드·괄호 불일치면 기동을 멈추고, 필수 필드 {asctime}·{levelname}·{appname}·{module}·{classname}·{funcName}·{message} 가 하나라도 없어도 멈춘다(config.REQUIRED_LOG_FIELDS). - SqlNoiseFilter 가 모든 핸들러에서 SQLAlchemy·드라이버 로거의 SQL 본문·바인딩 값을 막는다. LOG_SQL_ECHO_ENABLED=true 로만 열 수 있고, production/staging 에서는 설정 로드가 거부한다. - 비밀값 가리기 — app/utils/logs/redaction.py 의 SecretRedactor 가 규칙의 정본이다(DSN·URL 의 계정명과 비밀번호 scheme://***:***@host — 계정명 없는 scheme://:***@host·계정명만 있는 scheme://***@host, 비밀번호는 마지막 @ 까지, password·secret·token·api_key·authorization 으로 끝나는 키의 값, Bearer 토큰, JWT → ***). 여기에 config.LOG_REDACTED_SETTINGS(DB writer·replica 계정명·비밀번호, Redis 비밀번호, JWT access/refresh 키, SESSION_SECRET_KEY)의 현재 값 원문을 configure_logging() 이 넘겨, 로그 어디에 나와도 *** 로 바꾼다. 4글자 미만 값(주로 짧은 계정명)은 일반 단어와 겹치므로 user=·username= 뒤와 DSN 에서만 가린다. 새 비밀 설정은 이 목록에 넣어야 한다(test_every_secret_setting_is_redacted_from_logs 가 이름 규칙으로 강제). 가리기는 LogRecord factory 에 걸려 렌더된 메시지·traceback 본문(exc_text 로 미리 포맷해 고정)·stack_info 를 레코드가 만들어질 때 가린다 — 우리가 포매터를 소유하지 않는 경로도 같은 규칙을 탄다. 예외 타입·체인·파일·줄은 남는다. 접속 로그(DB 저장)는 대상이 아니다(§6). - 세션 롤백 로그(app/core/db/session.py)는 ERROR 에 예외 타입과 소요시간만 남긴다 — DB 예외의 str() 에 실행된 SQL 과 바인딩 값이 들어 있고, 앱 로거 이름은 SqlNoiseFilter 를 통과하기 때문이다. 추적이 필요하면 DEBUG 레벨에서 같은 지점의 exc_info=True 상세 레코드가 트레이스백 전문을 남긴다. 그래서 production/staging 은 debug 모드 자체를 거부한다(§3.2). - Service 는 LoggerMixin 을 상속해 self.log 를 쓴다. 키 표·Django LOGGING 설정 대응표는 README "로깅" 절이 정본이다.

레벨 결정 — root 레벨은 LOG_LEVEL, 없으면 DEBUG 에 따라 DEBUG/INFO. console 레벨은 LOG_CONSOLE_LEVEL, 없으면 같은 규칙. LOG_APP_LEVELS 가 있으면 root 는 그중 가장 낮은 레벨까지 내려가고, 헤더별 컷은 AppLevelFilter 가 한다(지정 없는 헤더 = LOG_LEVEL). 명시값이 DEBUG 기본 계산보다 우선한다.

DEBUG LOG_LEVEL / LOG_CONSOLE_LEVEL console 에 나오는 것
false 미설정 / 미설정 INFO 이상
true 미설정 / 미설정 DEBUG 이상
false DEBUG / DEBUG DEBUG 이상 (앱 DEBUG 모드는 여전히 꺼짐)
무관 INFO / DEBUG INFO 이상 — root 가 먼저 거른다
무관 DEBUG / INFO INFO 이상

startup 로그의 (DEBUG=%s) 는 표시 값일 뿐 출력 조건이 아니다. INFO 가 안 보이면 위 두 설정과 핸들러부터 본다.
