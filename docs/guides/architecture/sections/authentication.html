7. 인증 (JWT)

아키텍처의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

7. 인증 (JWT)

OAuth2 password flow + JWT access/refresh(회전). 자격증명은 user 기능의 User.hashed_password 에 있고, auth 는 인증 로직만 담당한다(auth → user 의존은 의도된 예외). 목적마다 클래스 하나인 보안 부품은 app/core/security/ 에 있다 — user 기능(해시)과 다른 기능의 인증 의존성(토큰 검증)도 써야 하므로 core 에 둔다.

부품 위치 역할
PasswordHasher app/core/security/passwords.py pwdlib Argon2 해시. 기존 bcrypt($2…)는 이전 규칙(72바이트 절단)으로 검증하고 성공하면 Argon2 새 해시를 돌려준다. 타이밍 균등화 더미 해시도 Argon2
TokenService app/core/security/tokens.py PyJWT 발급·검증. claims sub·type·iat·nbf·exp·jti·iss·aud + access username·su(슈퍼유저 여부, bool 필수) / refresh fam. 실패는 원인과 무관하게 InvalidTokenException(401, 오류 코드 AUTH_INVALID_TOKEN)
RefreshTokenStore app/core/security/refresh_store.py Redis 에 미사용 refresh(auth:rt:{jti})·사용자 family 집합·family 폐기 표시를 둔다. 소비는 Redis GETDEL 하나
RateLimiter app/core/security/rate_limit.py Redis 고정 창(MULTI 안에서 INCR + EXPIRE NX + TTL). 초과는 TooManyRequestsException(429, Retry-After)
Principal · OwnershipPolicy app/core/security/principal.py 요청 주체(id·username·is_superuser, 불변)와 소유권 판정 ensure_can_modify(owner_id, principal) — 소유자 또는 슈퍼유저, 아니면 403

조립은 provider 함수가 한다(생성자 주입, service-hardening ADR-022). 여러 기능이 함께 쓰는 provider — get_password_hasher·get_token_service·get_ownership_policy(프로세스당 하나, lru_cache)와 get_refresh_token_store(Depends(get_redis), §3.4) — 는 app/core/security/dependencies.py 에 있고, 인증 기능(app/features/auth/dependencies/auth_dependencies.py)은 그것을 그대로 쓰면서 get_client_ip_resolver·get_rate_limiter·get_auth_service(session, hasher, tokens, store) 를 더한다.

메서드 경로 인증 요청 성공 실패
POST /api/v1/auth/register — JSON (비밀번호 8~128자) 201 409 사용자명 중복 · 422 · 429
POST /api/v1/auth/login — form (username·password) 200 401 · 422 · 429
POST /api/v1/auth/refresh — JSON {"refresh_token": ...} 200 401 무효·만료·재사용·폐기·비활성 · 422
POST /api/v1/auth/logout — JSON {"refresh_token": ...} 204 401 무효·만료 · 422
GET /api/v1/auth/me Bearer — 200 401

토큰 응답은 {"access_token", "refresh_token", "token_type": "bearer", "expires_in": <access 수명 초>} 다.

흐름

  1. login — login_rate_limit 의존성이 ip(AUTH_LOGIN_IP_MAX_ATTEMPTS)와 ip+소문자 username(AUTH_LOGIN_MAX_ATTEMPTS)을 AUTH_LOGIN_WINDOW_SECONDS 창으로 센다. ip 는 접속 로그와 같은 ClientIPResolver(TRUSTED_PROXY_HOPS, §6)로 정한다. AuthService.authenticate(/admin 로그인과 같은 verify_credentials)가 해시기를 asyncio.to_thread 로 부르고, bcrypt → Argon2 재해시가 있으면 UserRepository.update 로 flush 해 둔다. 새 family 로 토큰 쌍을 발급하고 refresh 의 jti 를 기록한 뒤 핸들러가 커밋하고 ip+username 카운터를 지운다.
  2. refresh — refresh 토큰을 검증하고 GETDEL auth:rt:{jti} 로 소비한다. 값이 없으면 이미 쓴 토큰의 재사용(탈취 신호)이라 그 family 를 폐기하고 401 — 정상 사용자가 가진 같은 family 의 최신 토큰도 함께 죽는다. family 가 폐기됐거나 사용자가 없거나 비활성이면 401(비활성·부재는 family 도 폐기). 통과하면 같은 family 로 새 쌍을 발급한다.
  3. logout — refresh 토큰의 family 를 폐기하고 jti 를 소비한다(멱등, 204). access 토큰은 만료(ACCESS_TOKEN_EXPIRE_MINUTES)까지 유효하다 — 즉시 폐기 목록은 두지 않고 짧은 수명으로 대신한다.
  4. /me — get_current_principal(아래 §7.1) → read-only 세션을 primary 에 고정(using_writer)한 UserRepository.get_by_id → 없거나 비활성이면 401. replica 에서 읽으면 복제 지연 중 가입 직후의 유효한 토큰이 401 이 되고 비활성화·삭제가 늦게 반영된다(e2e-policy-2 결정 5, integration-e2e F-008). 다른 읽기 라우팅은 그대로다. Redis 도 쓰기 세션도 쓰지 않는다.
  5. register — register_rate_limit(ip, AUTH_REGISTER_MAX_ATTEMPTS/AUTH_REGISTER_WINDOW_SECONDS) 뒤 Argon2 해시로 저장, 응답 DTO 검증 후 커밋.

access·refresh 수명(ACCESS_TOKEN_EXPIRE_MINUTES·REFRESH_TOKEN_EXPIRE_DAYS)은 README 세션·토큰 만료 표에 있다.

설정 기본값 설명
JWT_ALGORITHM HS256 HS256·HS384·HS512 만 허용. 검증은 이 값 하나만 받는다
JWT_ISSUER / JWT_AUDIENCE fastapi-project / fastapi-project-api 검증 시 일치해야 한다
JWT_LEEWAY_SECONDS 5 exp·nbf·iat 시계 오차 허용
AUTH_LOGIN_MAX_ATTEMPTS / AUTH_LOGIN_IP_MAX_ATTEMPTS / AUTH_LOGIN_WINDOW_SECONDS 5 / 20 / 60 로그인 레이트 리밋
AUTH_REGISTER_MAX_ATTEMPTS / AUTH_REGISTER_WINDOW_SECONDS 5 / 3600 회원가입 레이트 리밋
ACCESS_TOKEN_SECRET_KEY / REFRESH_TOKEN_SECRET_KEY change-this-... 서로 다른 값으로 배포 전 반드시 교체 — 기본값이면 누구나 토큰을 위조한다. staging/production 은 placeholder 이거나 두 키가 같으면 기동이 실패한다(validate_deployment_safety(), §3.2)
  • access 와 refresh 는 서명 키가 다르고, type claim 도 검사한다(키가 같게 설정돼도 종류 혼동을 막는 두 번째 벽).
  • 상수 시간 인증: 사용자가 없거나 비밀번호가 없는 계정도 더미 Argon2 해시로 검증 비용을 치러 응답 시간차로 사용자명 존재를 알 수 없게 한다. bcrypt 해시가 남은 사용자는 bcrypt 비용이 드는 동안만 시간이 다르다(로그인하면 Argon2 로 바뀐다).
  • 논블로킹 해싱: Argon2·bcrypt 는 asyncio.to_thread 로 이벤트 루프 밖에서 돈다.
  • API 인증은 세션을 쓰지 않는다: 메인 앱에는 세션 미들웨어가 없고, admin_session 쿠키를 보내도 API 는 401 이다. 세션 로그인은 /admin 전용이다(§8).

7.1 인가 — 주체·소유권·슈퍼유저

권한은 슈퍼유저/일반 2단계다(users.is_superuser). 인가는 core 의 주입 경로 하나(app/core/security/dependencies.py)로 한다 — 기능이 인가를 위해 user 기능을 import 하지 않는다(service-hardening C-11).

주입 하는 일 실패
oauth2_scheme OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login", auto_error=False) — OpenAPI 에 Bearer 스킴을 싣는다 헤더가 없으면 아래가 401
get_current_principal access 토큰 검증 → Principal(id, username, is_superuser). DB 조회 없음. request.state.user_id 를 채운다 401 UNAUTHORIZED(토큰 없음) · 401 AUTH_INVALID_TOKEN(만료·위조·su 누락·refresh 토큰). 401 의 WWW-Authenticate: Bearer 는 전역 핸들러가 붙인다
require_superuser 주체가 슈퍼유저인지 본다 403 FORBIDDEN
CurrentPrincipal / SuperuserPrincipal 위 두 의존성의 Annotated 별칭 — 핸들러 인자 타입으로 쓴다 —
OwnershipPolicy 서비스가 생성자로 받아 수정·삭제 전에 ensure_can_modify(owner_id, principal) 를 부른다. owner_id 가 None 이면 슈퍼유저만 403 FORBIDDEN

접근 수준 선언과 기본 거부(app/core/security/access.py, access-policy). 뷰는 경로 데코레이터의 dependencies=[...] 에 수준을 하나 적는다.

선언 실체 쓰는 곳
Public 아무것도 하지 않는 표식 의존성 안전한 메서드(GET·HEAD·OPTIONS) 공개
PublicWrite 아무것도 하지 않는 표식 의존성(다른 함수) 인증 없는 쓰기를 명시적으로 연다 — auth register·login·refresh·logout
LoginRequired Depends(get_current_principal) — 인자 CurrentPrincipal 도 같은 선언으로 본다 401
SuperuserRequired Depends(require_superuser) — 인자 SuperuserPrincipal 도 같은 선언으로 본다 401 · 403

create_app() 의 마지막 단계(라우터·health·docs·admin 설치 뒤)에서 AccessPolicyGuard().verify(app) 가 서빙되는 모든 APIRoute (FastAPI 0.141 의 _IncludedRouter 중첩을 effective_route_contexts() 로 펼친 것, include_in_schema=False 포함)의 의존성 트리를 재귀로 훑는다. 선언 없음 · 서로 다른 수준 동시 선언 · 쓰기 메서드에 Public · 안전한 메서드에 PublicWrite 가 하나라도 있으면 위반 목록 전체를 담은 ImproperlyConfigured 로 기동을 멈춘다. require_superuser 는 안에서 get_current_principal 을 쓰므로 슈퍼유저가 있으면 슈퍼유저 하나로 본다. 라우터 단위 dependencies 도 트리에 들어가므로 인정되지만 예시는 뷰 단위로 통일했다. FastAPI 가 붙이는 문서 경로(Starlette Route)와 Mount(/admin — 자체 세션 인증)는 대상이 아니다. 앱이 직접 등록한 Scalar /docs 는 APIRoute 라 Public 을 선언한다.

기능 공개 인증 소유자 또는 슈퍼유저 슈퍼유저
blog · sns · reply 목록·단건 조회 생성(작성자 author_id·author 는 서버가 주체로 채운다 — 본문 값은 무시) 수정·삭제(존재 확인 404 가 먼저) —
catalog 목록·단건 조회 — — 생성·수정·삭제
reports — — — 일별 매출
home — — — 접속 로그 조회 5종(뷰마다 SuperuserRequired)

auth register·login·refresh·logout /me — —
  • 비활성화(is_active True→False)·강등(is_superuser True→False)·비밀번호 변경·삭제는 그 사용자의 refresh family 와 /admin 관리 세션을 모두 폐기한다(커밋 전). 무엇을 지울지는 revocation_for_change(app/core/security/revocation.py, §8)가 변경 전 값과 비교해 정한다. 강등 시 refresh 폐기는 service-hardening 부터의 동작(test_demotion_revokes_refresh_families)이고, 관리 화면도 같은 규칙을 쓴다(admin-session-hardening ADR-010 — 관리 화면 경로 = API 경로). refresh 회전은 DB 를 다시 읽지만(비활성 거부·새 권한으로 발급) 기존 동작을 유지한다. 이미 발급된 access 는 만료(기본 15분)까지 유효하다 — 즉시 폐기 목록은 두지 않는다(§11.3).
  • author_id 가 없는 행(인가 리비전 a3c9e8f1b274 이전 데이터)은 슈퍼유저만 수정·삭제한다.
  • 정본은 뷰 선언이다. "모든 오퍼레이션이 분류됐는가" 는 기동 검사가 막고, tests/test_authorization_policy.py 의 표는 예시 정책이 의도한 수준인지 가드의 판정과 대조하는 회귀용이다(OpenAPI security 와도 교차 확인한다).
  • 첫 관리자는 uv run python -m scripts.create_superuser --username <이름> --email <메일> 로 만든다(이미 있으면 승격, 비밀번호는 --set-password 일 때만 바꾼다). 사용법은 README 「첫 관리자 만들기」.
