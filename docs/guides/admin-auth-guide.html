1. 개요와 범위 — 인증 체계는 둘이고, 세션은 /admin 전용이다

이 저장소에는 인증 체계가 두 개 있다. API(/api/...)는 OAuth2 password flow 로 받은 JWT Bearer 토큰으로, 관리 화면(/admin, SQLAdmin)은 로그인 화면에서 발급한 서명 세션 쿠키(admin_session)로 인증한다. 두 체계가 공유하는 것은 사용자 테이블(users)·비밀번호 검증 함수(verify_credentials)·레이트 리밋 부품(RateLimiter)과 그 한도 설정뿐이고, 자격 증명(토큰·쿠키)은 서로를 인정하지 않는다.

확인 결과 (2026-10-12)

세션 기반 인증은 /admin 에만 적용되고 API 인증과 다른 작업에는 쓰지 않는다 — 맞다. 코드와 테스트로 확인한 근거:

  • 메인 FastAPI 앱에는 SessionMiddleware 가 없다. 세션 미들웨어는 AdminAuthBackend.middlewares 로만 만들어지고 SQLAdmin 이 자기 하위 Starlette 앱에 붙인다(app/core/security/admin_auth.py:126, sqladmin Admin.__init__ 이 authentication_backend.middlewares 를 하위 앱 미들웨어로 넣는다). 테스트: tests/core/test_admin_login_flow.py::test_session_middleware_lives_only_in_the_admin_sub_app.
  • API 인증은 get_current_principal(app/core/security/dependencies.py:81)이 Authorization: Bearer 만 읽는다. 유효한 admin_session 쿠키를 직접 실어 보내도 /api/v1/auth/me·/api/v1/user/users 는 401 이다. 테스트: test_admin_session_cookie_does_not_authenticate_the_api.
  • 관리 세션 쿠키는 /admin 밖 응답에서 설정되지 않는다(쿠키 path 도 /admin). 테스트: test_admin_session_cookie_is_never_set_outside_admin.
  • SESSION_COOKIE_NAME(기본 session)은 접속 로그 미들웨어가 그 쿠키 값을 기록할 때만 읽는다(app/core/middlewares/user_info_middleware.py:54·:177) — 인증에는 쓰이지 않는다. 관리 쿠키 이름과 같으면 기동을 멈춘다(관리자 쿠키가 접속 로그에 남지 않게, app/core/apps/wiring.py:146).
  • SESSION_SECRET_KEY 의 소비처는 정확히 둘이다: ① 관리 세션 쿠키 서명(app/core/apps/wiring.py:162 → SessionMiddleware(secret_key=...)), ② 설정 검증(config.py 의 REQUIRED_WITHOUT_ENV_FILE·validate_deployment_safety() — placeholder·32자 미만 거부). 다른 코드는 이 키를 읽지 않는다.
  • Celery 태스크·접속 로그 저장·scripts/create_superuser.py 는 세션을 쓰지 않는다(요청 밖 세션 팩토리 background_session 으로 DB 에 직접 붙는다).

2. 구성도 — 어디에 무엇이 붙는가

메인 앱의 미들웨어 체인에는 세션이 없다. SQLAdmin 은 Admin(...) 생성 시 자기 하위 Starlette 앱을 /admin 에 마운트하고, 그 하위 앱의 미들웨어로 인증 백엔드가 준 SessionMiddleware 를 붙인다. 그래서 세션 쿠키는 /admin 요청에서만 해석된다. 모든 관리 라우트는 sqladmin 의 login_required 를 거쳐 백엔드의 authenticate 를 부른다.

주입 관계 — 누가 무엇을 생성자에 넣는가

AdminAuthBackend 는 협력 객체를 모두 생성자로 받는다. core 는 사용자 모델을 모르므로(계층 규칙: core 는 features 를 import 하지 않는다) 자격 확인은 auth 앱이 AuthConfig.ready() 에서 core 훅에 팩토리로 등록하고, create_admin() 이 관리 화면을 조립할 때만 그 팩토리를 부른다 — 접속 로그 sink 와 같은 방식이다. Redis 클라이언트는 lifespan 이 기동 때 만들기 때문에 조립 시점에는 없어서, 레이트 리미터는 요청 때 꺼내는 provider(lambda)로 넣는다. 로그인 화면 템플릿 객체는 Admin 이 만든 뒤에야 생기므로 조립 지점이 사후에 넣는다(app/core/apps/wiring.py:172).

3. 기동 결정 흐름 — 설정에서 마운트까지

관리 화면이 켜질지는 기동 때 한 번 정해진다. 예전 설정 이름 ADMIN(true=켬)은 ADMIN_DISABLED(true=끔)로 바뀌며 뜻이 뒤집혔다. 설정 클래스는 모르는 키를 조용히 버리므로(extra="ignore"), ADMIN=false 로 관리 화면을 끄던 배포가 그대로 올라오면 관리 화면이 켜진다 — 그래서 이 이름만은 validate_removed_settings() 가 감지해 기동을 멈춘다. 예전 무인증 승인 플래그는 남아 있어도 무시된다(로그인이 붙었으므로 뜻이 없다).

4. 로그인 시퀀스

로그인은 sqladmin 의 Admin.login 라우트가 받아 백엔드 login() 에 넘긴다. 백엔드가 False 를 돌려주면 sqladmin 이 같은 로그인 화면을 400 으로 다시 그리고, Response 를 돌려주면(CSRF 403·한도 초과 429) 그대로 내보내고, True 면 /admin/ 으로 302 한다. 로그인 화면의 GET 은 sqladmin 이 컨텍스트 없이 그리므로, 폼의 CSRF 토큰은 백엔드가 템플릿에 건 전역 함수 csrf_token(request) 가 세션에서 꺼낸다(없으면 만들어 세션에 둔다). 세션 쿠키는 응답이 나갈 때 SessionMiddleware 가 세션 dict 를 JSON → base64 → itsdangerous TimestampSigner 로 서명해 붙인다.

  • CSRF 토큰 확인이 가장 먼저다 — 폼의 csrf_token 을 세션의 값과 hmac.compare_digest 로 비교하고, 없거나 다르면 로그인 화면을 403 으로 다시 그린다. 레이트 리밋 카운터도 올리지 않으므로 위조 요청이 피해자의 시도 한도를 깎지 못한다. 다시 그린 화면은 같은 토큰을 실어 바로 재시도할 수 있다(AdminLoginCsrf, app/core/security/admin_auth.py:48·:160).
  • 레이트 리밋이 자격 확인보다 먼저다 — 한도를 넘으면 맞는 비밀번호도 막는다(무차별 대입 비용을 올린다). 카운터 키는 API 로그인(login:)과 접두사가 달라 서로의 한도를 소모하지 않는다(app/core/security/admin_auth.py:171·:221).
  • 사용자명은 소문자로 접어 SHA-256 으로 키에 넣는다(키 길이 고정, 원문을 Redis 에 남기지 않는다).
  • 자격 확인은 API 로그인과 같은 verify_credentials 다 — 없는 사용자도 더미 Argon2 검증 비용을 치러 응답 시간으로 계정을 열거할 수 없고, bcrypt 해시는 로그인 때 Argon2 로 옮겨 저장된다(app/features/auth/services/auth_service.py:27).
  • 성공하면 request.session.clear() 뒤 사용자 id 하나만 넣는다 — 로그인 전에 쿠키로 들고 온 값은 남지 않는다(세션 고정 방지, app/core/security/admin_auth.py:185).
  • 로그에는 결과·IP·사용자명(64자까지, repr)·성공 시 사용자 id 만 남는다. 비밀번호·해시는 어떤 경로로도 로그에 싣지 않는다.

5. 요청별 인증 흐름

모든 관리 라우트(목록·상세·생성·수정·삭제·내보내기)는 login_required 로 감싸져 있고, 매번 AdminAuthBackend.authenticate 를 부른다. 쿠키는 신원(사용자 id)만 증명하고 권한은 매번 DB 에서 다시 읽는다 — 그래서 강등·비활성화·삭제가 다음 요청에서 바로 반영된다. 비용은 관리 요청마다 사용자 PK 조회 한 번이다(관리 화면 트래픽에서는 무시할 수준).

7. 로그아웃 흐름

로그아웃은 세션을 비운다. 세션이 비면 SessionMiddleware 가 만료된 쿠키를 내려 브라우저에서 지운다. 서버에 세션 저장소가 없으므로 로그아웃 전에 복사해 둔 쿠키 값은 만료(8시간)까지 서명이 유효하다 — 다만 권한을 매 요청 DB 로 보므로, 그 계정을 강등·비활성화하면 그 복사본도 즉시 쓸모가 없어진다(§10 남은 위험).

남은 위험(의도적으로 수용)

  • 서버 측 세션 저장소가 없다 — 로그아웃 전에 복사해 둔 쿠키는 만료(8시간)까지 서명이 유효하다. 계정이 활성 슈퍼유저로 남아 있는 한 그 복사본으로 들어올 수 있다. 끊으려면 계정을 비활성화하거나 SESSION_SECRET_KEY 를 교체한다. (Redis 세션 저장소로 바꾸면 해소 — CRP admin-login R-001)
  • 로그인 이후 관리 폼에는 CSRF 토큰이 없다 — 로그인 폼은 토큰을 확인한다(2026-10-19). sqladmin 이 그리는 생성·수정·삭제 폼과 GET 로그아웃은 토큰 없이 SameSite=Strict·Path=/admin 쿠키가 1차 방어다. 아주 오래된 브라우저(SameSite 미지원)는 대상이 아니다. (CRP security-ops-hardening R-001)
  • 관리 화면 안의 세분 권한이 없다 — 슈퍼유저면 모든 ModelView 에 모든 동작이 열린다(사용자 생성은 막혀 있고 비밀번호 해시는 어디에도 나오지 않는다).
  • 레이트 리밋의 IP 정확도는 TRUSTED_PROXY_HOPS 에 달렸다 — 프록시 뒤에서 0 이면 모두가 프록시 IP 하나로 세어져 한 사람이 한도를 채우면 모두가 429 를 받는다.

배포 체크리스트

  1. 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true. 예전 ADMIN 줄을 .env·배포 환경에서 지운다(ADMIN=false 였다면 ADMIN_DISABLED=true).
  2. 쓴다면 scripts/create_superuser.py 로 첫 관리자를 만든다(이 계정이 /admin 로그인 계정).
  3. SESSION_SECRET_KEY 를 secrets.token_urlsafe(48) 값으로, 다른 두 비밀키와 다르게.
  4. HTTPS 로만 접근한다(staging/production 쿠키는 Secure). 내부망 전용이면 프록시에서 /admin 을 제한한다.
  5. 프록시 뒤면 TRUSTED_PROXY_HOPS 를 프록시 단 수로.
  6. 배포 후 확인: curl -s -o /dev/null -w '%{http_code}' https://<host>/admin/ → 302(켜짐) 또는 404(ADMIN_DISABLED=true).

키 교체

SESSION_SECRET_KEY 를 바꾸고 재기동하면 기존 쿠키의 서명이 모두 실패해 모든 관리자가 다시 로그인해야 한다. API 토큰(JWT)은 다른 키를 쓰므로 영향이 없다. 여러 인스턴스는 같은 키를 써야 한다(인스턴스마다 다르면 로그인이 번갈아 풀린다).

12. 확장할 때 주의

  • 새 관리 뷰: 기능 폴더의 admin.py 에 ModelView 를 만들고 admin_views 에 넣는다(uv run python -m scripts.new_app <name> --with-admin). 인증을 따로 붙이지 않는다 — /admin 전체가 백엔드 뒤에 있다. 비밀 컬럼(해시·토큰)은 목록·상세·폼·내보내기에서 모두 빼고 tests/core/test_admin_views.py 같은 검사로 고정한다.
  • 로그인 화면 템플릿: app/templates/admin/sqladmin/login.html(유지 대상). sqladmin 0.32 는 templates_dir 의 FileSystemLoader 를 패키지 템플릿보다 먼저 보므로 같은 이름으로 덮어쓴다. 지킬 것: 독립 문서(base 를 확장하지 않는다), 필드 이름 username·password, autocomplete·required·레이블 연결, 폼 action="{{ url_for('admin:login') }}" POST, error 는 자동 이스케이프(|safe 금지), 외부 JS 를 넣지 않는다. Bootstrap 버전을 바꾸면 integrity 를 실제 파일로 다시 계산한다(현재 5.3.8, sha384-sRIl4kxILFvY47J16cr9ZwB07vP4J8+LH7qKQnuqkuIAvNWLzeN8tE5YBujZqJLB). 화면 계약은 tests/core/test_admin_login_flow.py·tests/browser/test_admin_login.py 가 본다.
  • API 에 세션 인증을 섞지 않는다: 메인 앱에 SessionMiddleware 를 붙이거나 API 의존성이 admin_session 을 읽게 하면, 브라우저가 자동으로 붙이는 쿠키로 API 가 인증되어 CSRF 면이 API 전체로 넓어지고, 토큰의 짧은 수명·refresh 폐기 모델과 세션 모델이 한 경로에서 섞여 폐기 규칙이 모호해진다. API 는 Bearer 만, 관리 화면은 세션만 — test_session_middleware_lives_only_in_the_admin_sub_app 이 이 경계를 지킨다.
  • 권한을 세분하려면: sqladmin ModelView.is_accessible·is_visible 과 get_current_user_id 로 뷰별 판정을 붙인다. 판정은 DB 를 읽어야 한다(세션 값은 신원만 증명한다).
  • 자격 확인을 바꾸려면: AdminCredentials 계약(verify·is_admin)을 구현해 설치 앱의 ready() 에서 register_admin_credentials() 로 팩토리를 등록한다. core 를 고치지 않는다.
