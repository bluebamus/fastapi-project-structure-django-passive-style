1. 개요와 범위 — 인증 체계는 둘이고, 세션은 /admin 전용이다

이 저장소에는 인증 체계가 두 개 있다. API(/api/...)는 OAuth2 password flow 로 받은 JWT Bearer 토큰으로, 관리 화면(/admin, SQLAdmin)은 로그인 화면에서 발급한 Redis 서버 세션(쿠키 admin_session 에는 무작위 세션 ID 만)으로 인증한다. 두 체계가 공유하는 것은 사용자 테이블(users)·비밀번호 검증 함수(verify_credentials)·레이트 리밋 부품(RateLimiter)과 그 한도 설정, 그리고 Redis 서버뿐이고, 자격 증명(토큰·쿠키)은 서로를 인정하지 않는다.

2026-10-19 변경 — admin-session-hardening

관리 세션은 예전에 Starlette 서명 쿠키(내용 전체가 쿠키)였다. 지금은 쿠키에 세션 ID 만, 내용은 Redis 에 있어 로그아웃·강등·비활성화·삭제·비밀번호 변경 때 서버가 세션을 즉시 지운다. 로그인 이후의 생성·수정·삭제·로그아웃도 CSRF 토큰을 요구하고, 로그아웃은 POST 전용이다. 날짜 필터에는 기간(시작일~종료일) 연산이 생겼다.

확인 결과

세션 기반 인증은 /admin 에만 적용되고 API 인증과 다른 작업에는 쓰지 않는다 — 맞다. 코드와 테스트로 확인한 근거:

  • 메인 FastAPI 앱에는 세션 미들웨어가 없다. RedisSessionMiddleware·AdminCsrfMiddleware 는 AdminAuthBackend.middlewares 로만 만들어지고 SQLAdmin 이 자기 하위 Starlette 앱에 붙인다(sqladmin Admin.__init__ 이 authentication_backend.middlewares 를 하위 앱 미들웨어로 넣는다). 테스트: tests/core/test_admin_login_flow.py::test_session_middleware_lives_only_in_the_admin_sub_app · tests/core/test_admin_csrf.py::test_session_and_csrf_middlewares_live_only_in_the_admin_sub_app.
  • API 인증은 get_current_principal(app/core/security/dependencies.py)이 Authorization: Bearer 만 읽는다. 유효한 admin_session 쿠키를 직접 실어 보내도 /api/v1/auth/me·/api/v1/user/users 는 401 이다. 테스트: test_admin_session_cookie_does_not_authenticate_the_api.
  • 관리 세션 쿠키는 /admin 밖 응답에서 설정되지 않는다(쿠키 path 도 /admin). 테스트: test_admin_session_cookie_is_never_set_outside_admin.
  • SESSION_COOKIE_NAME(기본 session)은 접속 로그 미들웨어가 그 쿠키 값을 기록할 때만 읽는다(app/core/middlewares/user_info_middleware.py) — 인증에는 쓰이지 않는다. 관리 쿠키 이름과 같으면 기동을 멈춘다(관리자 세션 ID 가 접속 로그에 남지 않게, create_admin).
  • SESSION_SECRET_KEY 의 소비처는 정확히 둘이다: ① 관리 세션 ID → Redis 키 HMAC(default_admin_session_store → AdminSessionStore.key_for), ② 설정 검증(config.py 의 REQUIRED_WITHOUT_ENV_FILE·validate_deployment_safety() — placeholder·32자 미만 거부). 다른 코드는 이 키를 읽지 않는다.
  • Celery 태스크·접속 로그 저장은 관리 세션을 쓰지 않는다. scripts/create_superuser.py 는 세션을 읽지 않고, --set-password 로 비밀번호를 바꾼 뒤 그 사용자의 관리 세션을 지우기만 한다.

2. 구성도 — 어디에 무엇이 붙는가

메인 앱의 미들웨어 체인에는 세션이 없다. SQLAdmin 은 Admin(...) 생성 시 자기 하위 Starlette 앱을 /admin 에 마운트하고, 그 하위 앱의 미들웨어로 인증 백엔드가 준 RedisSessionMiddleware(바깥)와 AdminCsrfMiddleware(안쪽)를 붙인다 — 순서가 계약이다(CSRF 는 세션의 토큰을 읽는다). 그래서 세션 쿠키는 /admin 요청에서만 해석된다. 모든 관리 라우트는 sqladmin 의 login_required 를 거쳐 백엔드의 authenticate 를 부른다. 관리 세션과 로그인 레이트 리밋은 API 와 같은 Redis 를 쓰되 키 접두사가 다르다.

주입 관계 — 누가 무엇을 생성자에 넣는가

AdminAuthBackend 는 협력 객체를 모두 생성자로 받는다. core 는 사용자 모델을 모르므로(계층 규칙: core 는 features 를 import 하지 않는다) 자격 확인은 auth 앱이 AuthConfig.ready() 에서 core 훅에 팩토리로 등록하고, create_admin() 이 관리 화면을 조립할 때만 그 팩토리를 부른다. Redis 클라이언트는 lifespan 이 기동 때 만들기 때문에 조립 시점에는 없어서, 레이트 리미터와 세션 저장소는 요청 때 꺼내는 provider(lambda)로 넣는다. 백엔드는 부모(AuthenticationBackend) 생성자를 부르지 않는다 — 부모 생성자는 서명 쿠키 세션 미들웨어를 만든다. 로그인 화면 템플릿 객체는 Admin 이 만든 뒤에야 생기므로 조립 지점이 사후에 넣고, 그 순간 템플릿 전역 함수 csrf_token 이 걸린다. 마지막으로 require_post_logout(admin) 이 로그아웃 라우트를 POST 전용으로 바꾼다.

3. 기동 결정 흐름 — 설정에서 마운트까지

관리 화면이 켜질지는 기동 때 한 번 정해진다. 예전 설정 이름 ADMIN(true=켬)은 ADMIN_DISABLED(true=끔)로 바뀌며 뜻이 뒤집혔다. 설정 클래스는 모르는 키를 조용히 버리므로(extra="ignore"), ADMIN=false 로 관리 화면을 끄던 배포가 그대로 올라오면 관리 화면이 켜진다 — 그래서 이 이름만은 validate_removed_settings() 가 감지해 기동을 멈춘다. 관리 세션 만료 두 값은 설정 로드 때 검사한다. Redis 연결 자체는 lifespan 이 기동 때 확인한다(관리 화면이 켜져 있지 않아도 Redis 는 필수다).

4. Redis 세션 구조와 만료

세션은 두 부품으로 나뉜다. AdminSessionStore 는 저장·조회·삭제·사용자별 전체 폐기를 하고 미들웨어·폐기 훅(API 서비스·관리 화면·스크립트)·테스트가 함께 쓴다. ASGI RedisSessionMiddleware 는 요청마다 쿠키의 세션 ID 로 Redis 를 읽어 scope["session"] 에 dict 를 넣고, 응답 헤더가 나가기 직전에 저장·회전·삭제를 한다. request.session 인터페이스가 그대로라 인증 백엔드는 세션이 어디에 저장되는지 모른다.

5. 로그인 시퀀스

로그인은 sqladmin 의 Admin.login 라우트가 받아 백엔드 login() 에 넘긴다. 그 앞에서 AdminCsrfMiddleware 가 토큰을 먼저 본다. 백엔드가 False 를 돌려주면 sqladmin 이 같은 로그인 화면을 400 으로 다시 그리고, Response 를 돌려주면(한도 초과 429) 그대로 내보내고, True 면 /admin/ 으로 302 한다. 로그인 화면의 GET 은 sqladmin 이 컨텍스트 없이 그리므로, 폼의 CSRF 토큰은 백엔드가 템플릿에 건 전역 함수 csrf_token(request) 가 세션에서 꺼낸다(없으면 만들어 세션에 둔다). 세션은 응답 헤더가 나가기 직전에 RedisSessionMiddleware 가 Redis 에 저장하고, 새 세션이면 쿠키에 세션 ID 를 싣는다.

  • CSRF 토큰 확인이 가장 먼저다 — 로그인 POST 도 다른 상태 변경 요청과 같은 미들웨어(AdminCsrfMiddleware)가 본다(검사는 한 곳). 없거나 다르면 로그인 화면을 403 으로 다시 그린다. 레이트 리밋 카운터도 올리지 않으므로 위조 요청이 피해자의 시도 한도를 깎지 못한다. 실패해도 세션의 토큰은 그대로라 다시 그린 화면으로 바로 재시도할 수 있다.
  • 레이트 리밋이 자격 확인보다 먼저다 — 한도를 넘으면 맞는 비밀번호도 막는다(무차별 대입 비용을 올린다). 카운터 키는 API 로그인(login:)과 접두사가 달라 서로의 한도를 소모하지 않는다.
  • 사용자명은 소문자로 접어 SHA-256 으로 키에 넣는다(키 길이 고정, 원문을 Redis 에 남기지 않는다).
  • 자격 확인은 API 로그인과 같은 verify_credentials 다 — 없는 사용자도 더미 Argon2 검증 비용을 치러 응답 시간으로 계정을 열거할 수 없고, bcrypt 해시는 로그인 때 Argon2 로 옮겨 저장된다.
  • 성공하면 request.session.clear() 뒤 사용자 id 를 넣고 새 CSRF 토큰을 만들고, RedisSessionMiddleware.rotate(request.scope) 로 세션 ID 회전을 명시적으로 요청한다. 미들웨어는 응답 직전에 새 세션 ID 를 발급하고 이전 Redis 키를 지운다 — 로그인 전에 심어 둔 세션 ID 는 로그인 뒤 쓸모가 없다(세션 고정 방지).
  • 로그에는 결과·IP·사용자명(64자까지, repr)·성공 시 사용자 id 만 남는다. 비밀번호·해시·세션 ID 는 어떤 경로로도 로그에 싣지 않는다.

7. CSRF 보호 — 토큰 하나, 검사는 미들웨어 한 곳

synchronizer token 패턴이다. 토큰은 관리 세션(Redis)에 하나(AdminCsrf, 세션 키 csrf_token) 있고 secrets.token_urlsafe(32) 로 만든다. 로그인 성공 시 세션을 비우고 새로 만든다(회전). 세션에 토큰이 없으면 거부한다. 다른 사이트는 이 화면을 읽을 수 없으므로 토큰을 모르고, SameSite=Strict 쿠키는 교차 사이트 요청에 실리지도 않는다 — 두 겹이다.

서버 — AdminCsrfMiddleware

  • 관리 하위 앱에서 세션 미들웨어 안쪽에 있다. /admin 아래 POST·PUT·PATCH·DELETE 전부(로그인 포함)를 본다. GET·HEAD·OPTIONS·TRACE 는 보지 않는다(조회라는 전제).
  • 토큰 위치는 헤더 X-CSRF-Token 이 우선이고, 없으면 폼 필드 csrf_token 이다. 폼(urlencoded·multipart)은 본문을 한 번 버퍼링해 파싱하고, 같은 본문을 receive 로 다시 흘려 준다 — 그냥 읽으면 sqladmin 이 폼을 다시 못 읽는다. 헤더가 있으면 본문을 읽지 않는다.
  • 비교는 hmac.compare_digest(상수 시간). 실패 응답은 백엔드의 csrf_failed 가 만든다 — 로그인은 로그인 화면 403, 로그인한 세션은 관리 화면 error.html 403, 로그인 전 요청은 문구만 403(text/plain, 관리 메뉴의 모델 이름을 그리지 않는다). 문구는 모두 요청이 만료되었습니다. 다시 시도하세요.
  • 로그는 WARNING [AdminCsrf] 토큰 불일치 METHOD PATH(예: [AdminCsrf] 토큰 불일치 POST /admin/user/edit/1).

클라이언트 — 덮어쓴 sqladmin/base.html

app/templates/admin/sqladmin/base.html 은 sqladmin 원본(sqladmin_original/base.html, sqladmin ChoiceLoader 의 원본 접두사)을 확장한다 — 복사하지 않는다. 바꾼 블록은 둘이다.

  • head_meta: 원본 + <meta name="csrf-token" content="{{ csrf_token(request) }}">.
  • tail_js: 원본 스크립트(jQuery·main.js) 뒤에 인라인 스크립트 하나 — 같은 출처 POST 폼 제출에 hidden csrf_token 을 붙이고, 같은 출처 XMLHttpRequest·fetch 에 X-CSRF-Token 헤더를 붙이고, 로그아웃 링크 클릭을 토큰 실은 POST 폼 제출로 바꾼다. 다른 출처 요청에는 토큰을 싣지 않는다.

10. 즉시 폐기 — API 와 관리 화면이 같은 UserSessionRevoker, 커밋 전에

AdminSessionStore.revoke_user(user_id) 는 admin:user_sessions:{user_id} 집합에 든 세션 키 전부와 집합을 지운다 — 그 사용자가 여러 브라우저에서 로그인했어도 모두 끊긴다(다른 사용자의 세션은 그대로). 무엇을 지울지는 판정 한 곳이 정한다 — revocation_for_change(before, changes) 가 변경 전 사용자와 바꿀 값을 비교해 Revocation(admin_sessions, refresh) 를 돌려주고, 삭제는 REVOKE_ON_DELETE, 비밀번호 변경 스크립트는 REVOKE_ON_PASSWORD_CHANGE(둘 다 두 집합 모두)다. UserSessionRevoker.revoke(user_id, revocation)(app/core/security/revocation.py)는 판정대로 RefreshTokenStore.revoke_user(API refresh family)·AdminSessionStore.revoke_user(관리 세션)를 부르기만 한다. API(UserService, provider get_user_session_revoker)·관리 화면(UserAdmin, revoker_from_scope(request.scope))·스크립트가 같은 판정을 쓰므로 조건이 갈리지 않는다. 요청 경로의 폐기는 모두 DB 커밋 전이다 — Redis 폐기가 실패하면 예외가 커밋을 막아 "DB 는 바뀌었는데 세션은 살아 있는" 상태가 남지 않는다(fail-closed).

남은 위험(의도적으로 수용 — CRP admin-session-hardening)

  • R-001 사용자 정의 @action 은 CSRF 보호 밖이다 — sqladmin 의 @action 은 GET 라우트라 미들웨어가 보지 않는다. 이 저장소의 관리 뷰는 쓰지 않는다. 상태를 바꾸는 작업을 더하려면 @expose(methods=["POST"]) 로 노출하거나 확인 모달이 토큰을 싣게 하고 원본 대조 테스트에 항목을 더한다.
  • R-002 405 의 Allow 가 불완전하다 — 같은 경로를 메서드별 라우트로 나눈 경우 실제 허용 메서드 전부가 아니다. 사용자 결정으로 현행 유지(2026-10-19). 기능·보안 영향이 없고 고치려면 라우터 내부 구조에 의존해야 한다.
  • R-003 익명 로그인 화면 방문도 Redis 세션을 만든다 — CSRF 토큰 때문이다. 미사용 만료(30분)로 사라지지만 대량 요청이면 Redis 메모리를 쓴다.
  • R-004 CSRF 미들웨어가 폼 본문을 메모리에 버퍼링한다 — 헤더 토큰이 없는 폼 요청만, /admin 한정, 상한 없음. 앞단 프록시의 본문 상한이 1차 방어다.
  • R-005 폐기는 커밋 전이다 — Redis 폐기가 실패하면 변경이 커밋되지 않는다(fail-closed). 반대로 폐기 뒤 DB 커밋이 다른 이유로 실패하면 세션만 지워진다(다시 로그인하면 된다). 폐기와 커밋 사이 짧은 틈에 다시 로그인해 생긴 세션은 커밋 뒤 매 요청 DB 확인이 다음 요청에서 막는다(ADR-008).
  • R-006 같은 세션의 동시 요청은 마지막 쓰기가 남는다 — 내용이 바뀌는 경우는 로그인·CSRF 토큰 생성뿐이다.
  • R-007 (해소) — API 와 관리 화면이 같은 판정(revocation_for_change)으로 같은 집합(관리 세션 + refresh)을 지운다. 이미 발급된 access 는 15분 만료까지 유효하다(security-ops-hardening ADR-006).
  • R-008 Redis 를 읽을 수 있는 사람은 세션 내용(사용자 id·CSRF 토큰)을 본다 — Redis 접근 통제는 배포의 몫이다. 쿠키(세션 ID)는 HMAC 때문에 Redis 키에서 만들 수 없다.
  • 관리 화면 안의 세분 권한이 없다 — 슈퍼유저면 모든 ModelView 에 모든 동작이 열린다(사용자 생성은 막혀 있고 비밀번호 해시는 어디에도 나오지 않는다).
  • 레이트 리밋의 IP 정확도는 TRUSTED_PROXY_HOPS 에 달렸다 — 프록시 뒤에서 0 이면 모두가 프록시 IP 하나로 세어져 한 사람이 한도를 채우면 모두가 429 를 받는다.

예전에 남은 위험이던 "서버 측 세션 저장소가 없어 복사한 쿠키가 8시간 유효"(admin-login R-001·security-ops-hardening R-003)와 "로그인 이후 폼·GET 로그아웃에 CSRF 토큰이 없음"(security-ops-hardening R-001)은 admin-session-hardening(2026-10-19)으로 해소됐다.

  1. 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true. 예전 ADMIN 줄을 .env·배포 환경에서 지운다(ADMIN=false 였다면 ADMIN_DISABLED=true).
  2. 쓴다면 scripts/create_superuser.py 로 첫 관리자를 만든다(이 계정이 /admin 로그인 계정).
  3. SESSION_SECRET_KEY 를 secrets.token_urlsafe(48) 값으로, 다른 두 비밀키와 다르게. 모든 인스턴스가 같은 값을 쓴다.
  4. Redis 가 필수다 — 관리 세션이 Redis 에 있다. Redis 를 인증·사설망으로 두고(세션 내용을 읽을 수 있는 사람을 줄인다, R-008), 메모리 여유를 본다(R-003).
  5. ADMIN_SESSION_MAX_AGE_SECONDS·ADMIN_SESSION_IDLE_SECONDS 를 보안 정책에 맞춘다(기본 8시간·30분).
  6. HTTPS 로만 접근한다(staging/production 쿠키는 Secure). 내부망 전용이면 프록시에서 /admin 을 제한한다. 앞단 프록시에 요청 본문 상한을 둔다(R-004).
  7. 프록시 뒤면 TRUSTED_PROXY_HOPS 를 프록시 단 수로.
  8. 배포 후 확인: curl -s -o /dev/null -w '%{http_code}' https://<host>/admin/ → 302(켜짐) 또는 404(ADMIN_DISABLED=true). 503 이면 Redis 를 본다.

키 교체

SESSION_SECRET_KEY 를 바꾸고 재기동하면 기존 쿠키의 세션 ID 로 Redis 키를 다시 계산할 수 없어 모든 관리자가 다시 로그인해야 한다(옛 키로 만든 Redis 키는 TTL 로 사라진다). API 토큰(JWT)은 다른 키를 쓰므로 영향이 없다. 여러 인스턴스는 같은 키를 써야 한다(인스턴스마다 다르면 로그인이 번갈아 풀린다). 특정 사용자만 끊으려면 키를 바꾸지 말고 그 계정을 비활성화하거나 --set-password 로 비밀번호를 바꾼다(즉시 폐기).

15. 목록 날짜·기간 필터

관리 목록의 시각 컬럼(created_at, UTCDateTime) 필터는 LocalDateFilter 다. sqladmin 의 연산 필터는 이 컬럼을 날짜로 알아보지 못해 문자열을 바인딩하고 목록이 500 이 된다. 이 필터는 YYYY-MM-DD 를 TIME_ZONE 의 날짜로 읽어 지역 0시를 UTC 순간으로 바꾼 범위로 거른다(DST 가 있는 날도 그날의 오프셋을 쓴다). 조회(GET)라 CSRF 토큰이 필요 없다.

연산값조건(지역 날짜 → UTC)
on 같은 날DD 0시 <= t < D+1 0시
from 이후(포함)Dt >= D 0시
before 이전(미포함)Dt < D 0시
between 기간(양 끝 포함)S~ES 0시 <= t < E+1 0시. S~ 는 S 이후, ~E 는 E 까지(열린 구간)
  • sqladmin 은 필터 값을 하나만 넘긴다. 그래서 화면(app/templates/admin/sqladmin/filters/local_date_filter.html)은 연산 선택 + 시작일·종료일 날짜 입력 두 개(이름 없음) + hidden 값 하나로 그리고, 제출 직전 작은 스크립트가 기간이면 S~E, 아니면 시작일을 hidden 에 넣는다.
  • 빠른 선택: 오늘(on)·최근 7일·최근 30일(between, 오늘 포함).
  • 역순 기간·형식 오류·구분자 없음·둘 다 빈 값이면 필터를 적용하지 않고 목록을 그대로 보여 준다 — WARNING [admin] 날짜 필터 기간 무시 parameter=….
  • created_at 이 있는 모든 ModelView 가 단다 — 새 뷰는 LocalDateFilter(Model.created_at, title="생성일"). 테스트: tests/core/test_admin_pages.py::test_period_filter_narrows_every_created_at_list.

16. 확장할 때 주의

  • 새 관리 뷰: 기능 폴더의 admin.py 에 ModelView 를 만들고 admin_views 에 넣는다(uv run python -m scripts.new_app <name> --with-admin). 인증·CSRF 를 따로 붙이지 않는다 — /admin 전체가 세션·CSRF 미들웨어와 백엔드 뒤에 있다. 비밀 컬럼(해시·토큰)은 목록·상세·폼·내보내기에서 모두 빼고 tests/core/test_admin_views.py 같은 검사로 고정한다.
  • 상태를 바꾸는 사용자 정의 작업: GET @action 으로 만들지 않는다(CSRF 보호 밖, R-001). @expose(methods=["POST"]) 로 노출하면 미들웨어가 토큰을 보고, 화면 스크립트가 같은 출처 POST·XHR·fetch 에 토큰을 붙인다. 원본 대조 테스트에 항목을 더한다.
  • 권한을 빼앗는 새 경로(비활성화·강등·삭제·비밀번호 변경)를 만들면 revocation_for_change(또는 REVOKE_ON_DELETE)로 판정해 UserSessionRevoker.revoke(user_id, revocation) 를 커밋 전에 부른다(조건을 따로 쓰지 않는다) — API 는 주입(get_user_session_revoker), 관리 화면 훅은 revoker_from_scope(request.scope), 요청 밖 스크립트는 revoke_sessions_in_redis 처럼 직접 조립한다. Redis 오류는 삼키지 않는다(커밋을 막게 둔다).
  • 세션에 값을 더할 때: 자주 바뀌는 값을 두지 않는다 — 동시 요청은 마지막 쓰기가 남는다(R-006). 신원 외의 권한 판단은 DB 에서 한다.
  • 로그인 화면 템플릿: app/templates/admin/sqladmin/login.html(유지 대상). sqladmin 0.32 는 templates_dir 의 FileSystemLoader 를 패키지 템플릿보다 먼저 보므로 같은 이름으로 덮어쓴다. 지킬 것: 독립 문서(base 를 확장하지 않는다), 필드 이름 username·password, hidden csrf_token(csrf_token(request)), autocomplete·required·레이블 연결, 폼 action="{{ url_for('admin:login') }}" POST, error 는 자동 이스케이프(|safe 금지), 외부 JS 를 넣지 않는다. Bootstrap 버전을 바꾸면 integrity 를 실제 파일로 다시 계산한다(현재 5.3.8, sha384-sRIl4kxILFvY47J16cr9ZwB07vP4J8+LH7qKQnuqkuIAvNWLzeN8tE5YBujZqJLB). 화면 계약은 tests/core/test_admin_login_flow.py·tests/browser/test_admin_login.py 가 본다.
  • 로그인 이후 화면 템플릿: app/templates/admin/sqladmin/base.html(유지 대상)은 원본을 확장해 head_meta·tail_js 두 블록만 바꾼다. 원본을 복사해 오지 않는다. sqladmin 을 올리면 tests/core/test_admin_csrf.py 의 원본 대조 테스트를 먼저 본다.
  • API 에 세션 인증을 섞지 않는다: 메인 앱에 세션 미들웨어를 붙이거나 API 의존성이 admin_session 을 읽게 하면, 브라우저가 자동으로 붙이는 쿠키로 API 가 인증되어 CSRF 면이 API 전체로 넓어지고, 토큰의 짧은 수명·refresh 폐기 모델과 세션 모델이 한 경로에서 섞여 폐기 규칙이 모호해진다. API 는 Bearer 만, 관리 화면은 세션만 — test_session_middleware_lives_only_in_the_admin_sub_app 이 이 경계를 지킨다.
  • 권한을 세분하려면: sqladmin ModelView.is_accessible·is_visible 과 get_current_user_id 로 뷰별 판정을 붙인다. 판정은 DB 를 읽어야 한다(세션 값은 신원만 증명한다).
  • 자격 확인을 바꾸려면: AdminCredentials 계약(verify·is_admin)을 구현해 설치 앱의 ready() 에서 register_admin_credentials() 로 팩토리를 등록한다. core 를 고치지 않는다.
