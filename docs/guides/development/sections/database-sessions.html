4. 세션·트랜잭션·비동기 작성 규칙

개발·확장의 세부 주제입니다. 목적·책임·운영 및 확장 시 지켜야 할 계약을 설명합니다.

4. 세션·트랜잭션·비동기 작성 규칙

4.1 세션 선택

flowchart TD U[유스케이스] --> Q{쓰기 / 조회 후 쓰기 / 잠금?} Q -- 예 --> W[get_writer_db_session
응답 전 한 번 commit] Q -- 아니오 --> L{복제 지연을 허용하는 조회?} L -- 예 --> R[get_read_only_db_session
commit 없음] L -- 아니오 --> C[writer 고정 조회
get_writer_db_session 또는 using_writer]

HTTP 메서드 이름만으로 판단하지 않는다. 한 원자 작업에 여러 Service 가 참여하면 같은 writer 세션을 주입하고 커밋 주체를 하나로 둔다. 인가(CurrentPrincipal)는 DB 를 읽지 않는다. 사용자 엔티티가 필요한 인증(get_current_user)은 read-only 세션을 따로 쓰되 primary 에 고정해 읽으므로(복제 지연 중에도 가입 직후 토큰이 통하고 비활성화가 즉시 반영된다), 인증 단계에서 읽은 객체를 쓰기 세션에서 수정하려면 쓰기 세션에서 다시 조회한다.

4.2 커밋과 응답

  • 쓰기 view 는 성공 응답을 만들기 전에 정확히 한 번 커밋한다. 조회 Dependency 는 커밋하지 않는다.
  • 순서는 응답 DTO 검증 → commit → 반환 하나다(§2.8). 모든 기능의 생성·수정 핸들러가 이 순서를 따른다. 반대로 하면 DTO 검증 실패가 500 을 내는데 데이터는 이미 커밋돼 남는다. 회귀 가드: tests/test_validate_before_commit.py (전 기능의 생성·수정 핸들러에서 DTO 검증을 실패시켜 500·커밋 0회·DB 불변을 확인). 커밋을 Dependency teardown 에 두지 않는다.
  • DTO 가 접근할 관계·컬럼은 Repository 에서 명시적으로 로드한다. 커밋 이후나 DTO 검증 중 lazy load 가 암묵 I/O 를 일으키지 않게 한다 (expire_on_commit=False 가 모든 관계 로딩을 해결하지는 않는다).
  • PATCH 스키마의 None 은 "미전달"과 다르다. exclude_unset=True 는 안 보낸 필드만 뺀다. 그래서 수정 스키마는 app/core/schemas.py 의 PatchSchema 를 상속한다 — 보낸 필드의 null 은 nullable_fields(모델 컬럼이 nullable=True 인 것만 적는다) 밖이면 422 다. 예: ProductUpdate.nullable_fields = frozenset({"description"}) 라 {"name": null} 은 422, {"description": null} 은 설명을 지운다.
  • 상태 전환·재고 차감처럼 동시성이 있는 변경은 "조회 후 UPDATE" 만으로 안전하지 않다. 조건부 UPDATE·잠금·DB 제약을 설계한다.
  • 커밋 성공 뒤 응답이 유실될 수 있다. 중요한 생성 업무는 멱등 키·중복 처리 정책을 정한다.

4.3 N+1 과 목록

Eager loading·집계·정렬 목록은 Base 가 아니라 기능 Repository 에 둔다.

class UserRepository(BaseRepository[User]):
    model = User

    async def get_all_with_posts(self, *, skip: int = 0, limit: int = 50) -> Sequence[User]:
        stmt = (
            select(User)
            .options(selectinload(User.posts))   # 1:N 은 selectinload 가 기본
            .order_by(User.id)                   # 정렬 없는 pagination 은 페이지가 겹친다
            .offset(skip)
            .limit(limit)
        )
        return (await self.session.execute(stmt)).scalars().all()
# joinedload: 1:1 / 작은 N:1, subqueryload: 복잡한 관계

(예시의 User.posts 관계는 현재 모델에 없다 — 패턴 설명용이다.)

4.4 비동기 원칙

  • async def 는 await 하는 I/O 동안 다른 요청을 진행시킬 뿐, CPU 연산이나 동기 SDK 를 비동기로 바꾸지 않는다. async endpoint 에서 time.sleep·동기 HTTP·큰 파일 처리·무거운 CPU 루프를 직접 돌리지 않는다. 짧은 CPU 작업(JWT·Pydantic·User-Agent 파싱)은 그대로 두고, 비밀번호 해시(Argon2)처럼 비싼 것은 asyncio.to_thread 로 뺀다. 무거운·내구성이 필요한 작업은 Celery 로 보낸다.
  • 같은 AsyncSession 으로 asyncio.gather 하지 않는다. 한 트랜잭션의 SQL 은 순차 await, 독립 병렬 작업은 작업별 세션을 연다.
  • 요청의 세션·Service·Request 를 백그라운드나 Celery 로 넘기지 않는다. 요청 밖에서는 직접 조립한다.
async with background_session() as session:     # 요청 밖 — 커밋은 직접
    await SomeService(session).do_write()
    await session.commit()
  • Celery 태스크는 기능 루트 tasks.py 에 두고(INSTALLED_APPS 에 있으면 워커가 자동으로 include 한다) run_async() 로 코루틴을 돌린다. 세션은 background_session() 으로 열고, 서비스는 그 기능의 provider 함수(세션을 받는 일반 함수 — 예: home build_user_access_log_service(session))로 조립한다 — HTTP 의존성도 같은 함수를 부른다. 인자는 JSON 직렬화 가능한 값만. 재시도·중복·커밋과 enqueue 사이 실패를 테스트한다.
  • 주기 실행이 필요하면 같은 tasks.py 에서 celery_app.add_periodic_task(crontab(...), my_task.s(), name="<앱>.<태스크>") 로 등록한다 — 중앙 Celery 앱에 목록을 만들지 않는다(예: home tasks.PURGE_SCHEDULE). 시각은 TIME_ZONE 기준이고, 실행에는 worker 와 별도로 beat 가 한 개 필요하다: uv run celery -A app.celery.app beat --loglevel=info. 대량 삭제는 배치로 나눠 배치마다 커밋한다(home purge_expired 참고).
  • 접속 로그 runner(access_log_tasks)는 drop 가능한 비핵심 작업 전용이다. 업무 저장·결제·발송을 넣지 않는다.
  • Redis 는 필수다. 새 기능은 redis: Redis = Depends(get_redis)(app/core/redis.py)로 lifespan 이 소유한 client 를 주입받는다 — Redis.from_url 을 직접 만들지 않는다. client 가 없으면(lifespan 밖) 503. 테스트는 app.state.redis 에 fakeredis 를 넣거나 dependency_overrides[get_redis] 를 쓴다. 지원 최소 버전은 redis.REDIS_MIN_VERSION(7.0 — EXPIRE NX)이다. 더 새 명령·옵션을 쓰면 그 상수와 근거 표를 함께 올린다 — tests/core/test_redis_version.py 가 소스의 명령과 상수를 대조한다.

4.5 인증·인가 붙이기

인가는 core 의 주입 경로(app/core/security/dependencies.py) 하나로 건다 — 기능이 인가를 위해 user·auth 기능을 import 하지 않는다. 권한은 슈퍼유저/일반 2단계다. 정책 전체 표는 아키텍처 §7.1.

모든 뷰는 접근 수준을 하나 선언한다(app/core/security/access.py). 선언이 없거나, 둘 이상이거나, 쓰기 메서드에 Public· 조회 메서드에 PublicWrite 를 적은 라우트가 있으면 create_app() 이 위반 목록 전체를 담은 ImproperlyConfigured 로 기동을 멈춘다 (AccessPolicyGuard — 기본 거부). 사용자 정보가 필요한 뷰는 인자로 받으면 그것이 선언이다 — 데코레이터에 같은 수준을 또 적지 않는다.

필요 쓰는 것 실패
공개 조회(GET) dependencies=[Public] —
인증 없는 쓰기(가입·로그인 류) dependencies=[PublicWrite] — 일부러 연다는 표시 —
로그인한 사용자 핸들러 인자 principal: CurrentPrincipal, 결과가 필요 없으면 dependencies=[LoginRequired] 401
슈퍼유저 인자 principal: SuperuserPrincipal, 결과가 필요 없으면 dependencies=[SuperuserRequired] 401 · 403
작성자만 수정 서비스가 생성자로 OwnershipPolicy 를 받고 ensure_can_modify(row.author_id, principal) 403
사용자 엔티티(활성 여부 포함) auth 의 get_current_user — DB 를 읽는다. 인가만 필요하면 쓰지 않는다 401 
# dependencies/<name>_dependencies.py — 정책 객체도 provider 로 주입한다
async def get_item_service(
    session: AsyncSession = Depends(get_writer_db_session),
    ownership: OwnershipPolicy = Depends(get_ownership_policy),
) -> ItemService:
    return ItemService(session, ownership)

# services/<name>_service.py — 존재 확인(404) 뒤 소유권(403)
async def update_item(self, item_id: str, data: ItemUpdate, principal: Principal) -> Item:
    existing = await self.get_item(item_id)
    self.ownership.ensure_can_modify(existing.author_id, principal)
    ...

# api/routers/v1/<name>.py — 작성자는 서버가 주체로 채운다(요청 본문에서 받지 않는다)
@router.post("/items", ...)
async def create_item(payload: ItemCreate, principal: CurrentPrincipal, service: ItemService = Depends(get_item_service)):
    item = await service.create_item(payload, principal)   # author_id=principal.id

@router.get("/items", dependencies=[Public], ...)              # 공개 조회도 선언한다
@router.delete("/items/{item_id}", dependencies=[SuperuserRequired], ...)

함수를 감싸는 데코레이터(Django 식 @login_required)를 쓰지 않는 이유. FastAPI 는 핸들러의 시그니처를 읽어 의존성 주입·요청 검증·OpenAPI 를 만든다. 함수를 감싸면 그 시그니처가 래퍼 뒤로 숨어(functools.wraps 로 일부 되살려도 Depends·Annotated 해석과 security 문서화가 어긋나기 쉽다) 주입이 깨지거나 문서에서 인증 표시가 사라진다. 경로 데코레이터의 dependencies=[...] 는 FastAPI 가 원래 제공하는 "뷰 단위 선언" 이라 시그니처를 건드리지 않고, OpenAPI 의 Bearer 표시도 그대로 나온다. 다만 선언만으로는 "잊은 뷰" 가 열린 채 배포되므로 기동 검사가 기본 거부를 맡는다.

  • 보호 라우트는 responses 에 app/core/security/dependencies.py 의 공용 401·403 응답 상수를 싣는다(OpenAPI 에 문서화된다).
  • 예시 기능의 오퍼레이션을 바꾸면 tests/test_authorization_policy.py 의 회귀 표(public·public_write·auth·owner·self·admin)도 고친다 — 표는 가드의 판정과 대조된다. 새 기능의 "선언 여부" 는 표가 아니라 기동 검사가 본다.
  • 엔드포인트 테스트는 get_current_principal 을 override 하지 않고 tests/auth_headers.py 의 헤더(admin_headers()·user_headers())로 실제 토큰을 보낸다. 토큰 검증·su claim·request.state.user_id 기록까지 같이 시험된다.
  • Principal 은 토큰 claims 로 만든다(DB 조회 없음). 강등·비활성화가 즉시 반영돼야 하는 판정이면 DB 를 다시 읽는다.
  • API 에 세션(쿠키) 인증을 섞지 않는다. /admin 의 세션 로그인은 SQLAdmin 하위 앱 전용이다 — 메인 앱에 세션 미들웨어를 붙이거나 API 의존성이 admin_session 을 읽게 하면 쿠키 기반 CSRF 면이 API 로 넓어진다. 이유와 구조는 관리 화면 인증 가이드.
  • 새 기능의 admin.py ModelView 는 따로 인증을 붙이지 않는다 — /admin 전체가 AdminAuthBackend 뒤에 있다. 로그인 화면은 app/templates/admin/sqladmin/login.html 이 덮어쓴다(유지 대상, 수정 규칙은 가이드 §16). 폼의 CSRF hidden 입력 (csrf_token(request))을 지우면 모든 로그인이 403 이다. 로그인 이후 화면은 app/templates/admin/sqladmin/base.html 이 sqladmin 원본을 확장해 <meta name="csrf-token"> 과 토큰을 붙이는 스크립트를 싣는다 — 이 파일을 지우거나 블록을 바꾸면 생성·수정·삭제·로그아웃이 403 이다. sqladmin 을 올리면 tests/core/test_admin_csrf.py(원본 대조)가 먼저 깨진다 — 원본 블록·로그아웃 링크·main.js 요청 방식을 보고 스크립트를 맞춘다.
  • 관리 화면에 상태를 바꾸는 사용자 정의 작업을 더하면 GET @action 으로 만들지 않는다 — CSRF 미들웨어는 POST·PUT·PATCH·DELETE 만 본다 (admin-session-hardening R-001). POST 로 노출하고 원본 대조 테스트에 항목을 더한다.
  • 관리 세션은 Redis 서버 세션이다(app/core/security/admin_session.py). 사용자의 권한을 빼앗는 새 경로(비활성화·강등·삭제·비밀번호 변경)를 만들면 조건을 따로 쓰지 말고 revocation_for_change(변경 전 객체, 바꿀 값)(삭제는 revocation.REVOKE_ON_DELETE)로 판정해 UserSessionRevoker.revoke(user_id, revocation) (app/core/security/revocation.py)를 커밋 전에 부른다 — 비활성화·강등·비밀번호 변경·삭제는 관리 세션 + refresh 를 지운다(관리 화면 경로 = API 경로). Redis 오류는 삼키지 않는다 — 예외가 커밋을 막게 둔다. API 는 provider get_user_session_revoker 로 주입받고(UserService 생성자의 revoker), 관리 화면은 UserAdmin 의 on_model_change·on_model_delete 가 revoker_from_scope(request.scope) 로 부른다. after_* 훅(커밋 뒤)에서 폐기하지 않는다. 요청 밖 스크립트는 scripts/create_superuser.py 가 예시다.
  • 관리 화면 테스트 헬퍼는 tests/admin_login.py 에 있다 — admin_login()(로그인 화면의 hidden 토큰을 실어 POST), admin_page_token() (로그인 이후 화면의 meta 토큰 — 생성·수정 폼에는 csrf_token, 삭제 같은 XHR 흉내에는 X-CSRF-Token 헤더로 싣는다), admin_logout() (meta 토큰을 실어 POST /admin/logout). 로그아웃을 GET 으로 부르면 405 다. 세션이 Redis 에 있으므로 관리 화면 테스트는 app.state.redis 에 fakeredis(fakeredis.aioredis.FakeRedis)를 넣는다(tests/core/test_admin_login_flow.py 참고) — 없으면 관리 화면이 503 이다.
  • ModelView 의 시각 컬럼(UTCDateTime) 필터는 OperationColumnFilter 가 아니라 LocalDateFilter(Model.created_at, title="생성일") (app/core/admin_filters.py)로 단다 — 연산 필터는 문자열을 바인딩해 목록이 500 이 된다. 연산은 같은 날·이후·이전·기간(YYYY-MM-DD~YYYY-MM-DD, 양 끝 포함)이다.
