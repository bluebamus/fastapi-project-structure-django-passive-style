0. 목적과 설계 원칙

이 저장소는 Django 식으로 앱을 수동 설치하고, URL 은 라우터 파일로 수동 관리하는 FastAPI 프로젝트 골격이다. 한 문장으로 줄이면 다음과 같다.

앱의 설치 여부와 순서는 사람이 한 곳(config.INSTALLED_APPS)에서 명시하고, 설치된 앱 내부의 결선(Router·Models·Admin)은 컨벤션이 처리한다.

결정 주체
어떤 앱을, 어떤 순서로 설치할지 사람 — config.INSTALLED_APPS
설치된 앱의 Router·Models·Admin 결선 App Registry — AppConfig 컨벤션

0.1 원칙

  • 설치는 목록에만 있다. app/features/ 에 디렉터리를 만드는 것으로는 아무 일도 일어나지 않는다. 목록에서 빼면 디렉터리가 남아 있어도 route·registry 소유 모델·Admin·ready() 가 모두 빠진다. 대가로 설치 범위를 한 곳에서 읽고, 로드 순서를 목록 순서로 통제하며, 실험 중인 앱을 비활성으로 둘 수 있다.
  • URL 은 라우터 파일 계층이 소유한다. 프레임워크가 경로를 추론하지 않는다.

text v1/<view>.py 엔드포인트 경로 /products router.py 버전·기능 prefix, tag /v1/catalog, tags=["Catalog"] AppConfig 마운트 prefix /api → /api/v1/catalog/products

  • 기능 중심 구조. 한 기능의 Router·Dependency·Service·Repository·Model·Schema·Admin·테스트는 app/features/<name>/ 안에 둔다. 기능 단위로 복사·삭제할 수 있어야 "탈착 가능한 앱"이 성립한다.
  • 예측 가능한 트랜잭션 경계. 커밋은 쓰기 핸들러 본문이 응답 전에 한 번 한다(§4.5). 별도 UnitOfWork 계층은 두지 않는다.
  • 조용한 실패 금지. 선택 모듈 부재는 허용하지만, 모듈 안의 import 오류·공개 이름 누락·route 충돌은 기동 실패다.

0.2 의도적으로 택하지 않은 것

택하지 않은 것 이유
디렉터리 자동 스캔으로 앱 활성화 설치 범위와 순서가 파일 시스템 상태에 암묵적으로 끌려간다
main.py 에 include_router 를 앱마다 나열 앱이 늘수록 main.py 가 모든 기능 추가의 공유 편집 지점이 된다(한때 이 방식으로 되돌렸다가 registry 로 복귀했다 — §12)
기능 간 직접 import·FK·relationship 중심의 예제 앱 탈착성이 깨진다. 실제 제품에서 관계를 추가할 때는 앱 제거 가능성과 migration 순서를 함께 설계한다
관리 화면에 API 와 같은 JWT 를 쓰기 브라우저 화면은 서명 세션 쿠키가 표준이다. 대신 세션은 /admin 하위 앱에만 두고 API 인증과 섞지 않는다(§8)
인메모리 레이트 리밋 워커별로 카운터가 갈라져 실질 한도를 보장하지 못했다. 필요하면 프록시·게이트웨이에서 건다

2. App Registry — Django 식 수동 앱 설치

2.1 config.INSTALLED_APPS

INSTALLED_APPS: list[str] = [
    "app.features.home.apps.HomeConfig",
    "app.features.blog.apps.BlogConfig",
    "app.features.reply.apps.ReplyConfig",
    "app.features.sns.apps.SnsConfig",
    "app.features.user.apps.UserConfig",
    "app.features.auth.apps.AuthConfig",
    "app.features.catalog.apps.CatalogConfig",   # ORM 예제
    "app.features.reports.apps.ReportsConfig",   # Raw SQL 예제
]
  • 항목 형식은 Django 와 같다. config class 경로(권장)와 package 경로("app.features.blog" → blog.apps 에서 기본 config 선택) 둘 다 받는다. 짧은 이름("blog")은 받지 않는다.
  • 순서가 계약이다. population·ready()·Router 등록·Admin view 등록이 모두 이 순서를 따른다. 새 앱은 뒤에 붙인다.
  • 환경변수로 덮어쓰지 않는다. 설치 구성은 코드 리뷰 대상이다.
  • 새 프로세스에서 목록에서 뺀 앱은 결선 대상에서 빠진다. 다만 같은 프로세스에서 이미 import 한 매핑 클래스는 전역 Base.metadata 에 남는다. registry 를 새로 만들어도 SQLAlchemy metadata 가 청소되지는 않는다.

2.2 앱 패키지와 결선 컨벤션

# app/features/<name>/apps.py
from app.core.apps import AppConfig


class <Name>Config(AppConfig):
    name = "app.features.<name>"

기능 root __init__.py 는 가벼운 package marker 다. Router 도 Model 도 import 하지 않는다 — 1단계(root package import)에서 하위 모듈이 딸려오면 3단계 순서가 무너진다.

AppConfig 속성 기본값 의미
name (필수) 앱 package 전체 경로
label name 의 마지막 조각 유일해야 하고 유효한 Python identifier 여야 한다
verbose_name label 의 title 표현 예: SnsConfig 는 "SNS" 로 재정의
default None <package>.apps 에 config 가 여럿일 때 선택 표시
router_module / router_attribute api.routers.router / <label>_router Router 결선
models_module models 이 module 에 노출된 매핑 클래스 중 __module__ 이 앱 하위인 것을 수집 — models/__init__.py 에서 재노출해야 한다
admin_module admin 공개 이름 admin_views
tasks_module tasks Celery 태스크 module(선택). 워커 include 에 들어간다(§9)
router_prefix /api 마운트 prefix, 앱별 재정의 가능
구성요소 module 이 없으면 module 은 있는데 공개 이름이 없거나 내부 import 가 깨지면

Admin 관리 화면 없는 앱(정상) 기동 실패
Tasks 태스크 없는 앱(정상) 워커가 include 를 import 할 때 실패 — 발견은 find_spec 으로 존재만 본다(§9)

2.3 3단계 population

Apps.populate(INSTALLED_APPS)
  1) config/root package import   →  apps_ready = True
  2) models import                →  models_ready = True
  3) AppConfig.ready()            →  ready = True
  • 단계는 앱별이 아니라 phase 단위다. 모든 앱의 1단계가 끝난 뒤 2단계로 간다 — 어떤 ready() 든 모든 앱의 모델을 볼 수 있다.
  • 중복 항목, 중복 name, 중복 label, 잘못된 label, 해석할 수 없는 항목, AppConfig 가 아닌 class, 기본 config 를 고를 수 없는 경우(복수 후보에 default=True 가 하나가 아님)는 ImproperlyConfigured.
  • populate() 는 thread-safe(RLock)하고 멱등이다. 같은 목록으로 완료 후 재호출은 no-op, 다른 목록이면 ImproperlyConfigured(다른 구성은 새 Apps() 로 만든다), 진행 중 재진입은 RuntimeError (ready() 안에서 populate() 를 부르지 않는다). 실패하면 registry 상태를 되돌린 뒤 원래 예외를 전파한다 — 단, 이미 import 된 Python 모듈과 전역 metadata 까지 되돌리지는 않는다.
  • populate(..., run_ready=False) 는 1·2단계만 수행한다. Alembic·Celery 워커(app/celery/app.py)와 startup DDL 준비가 쓴다. 이후 같은 registry 에 run_ready=True 로 다시 부르면 3단계만 실행된다.
  • 조회 API: get_app_configs(), get_app_config(label), is_installed(name), get_models(), get_model(app_label, model_name)(대소문자 무시). 준비 전 조회는 AppRegistryNotReady, 없는 대상은 AppLookupError.
  • 전역 기본 registry 는 app.core.apps.apps. 테스트와 factory 는 Apps() 를 새로 만들어 주입할 수 있다.

2.4 wiring adapter (app/core/apps/wiring.py)

함수 동작
install_routers(app, registry) 설치 순서대로 <label>_router 를 router_prefix 로 마운트. 두 앱이 같은 method + 최종 path 를 등록하면 ImproperlyConfigured 로 기동 실패(먼저 등록된 쪽이 조용히 이기지 않는다)
install_admin(admin, registry) 설치 앱의 admin_views 를 선언 순서대로 add_view

app/core/apps/config.py·registry.py 는 FastAPI·SQLAdmin·SQLAlchemy 를 import 하지 않는다. Alembic·CLI 가 registry 를 써도 웹 스택이 딸려오지 않는다(tests/core/apps/test_core_independence.py, tests/core/test_admin_lazy_loading.py).

2.5 ready() 의 제약

ready() 는 process-local wiring 전용이다.

  • 허용: 모듈 전역 결선(예: HomeConfig.ready() 의 access-log sink 등록 — 현재 유일한 사용처), 다른 앱 모델 조회(apps.get_model(...))
  • 금지: DB 쿼리·커밋, network 호출, subprocess 실행, secret 출력

migration 과 CLI 도 이 hook 을 실행할 수 있기 때문이다(alembic upgrade 가 외부 연결을 만들면 배포가 예측 불가능해진다). Alembic 은 run_ready=False 로 hook 자체를 건너뛴다. 회귀 가드는 tests/core/apps/test_installed_apps.py 의 test_ready_hooks_perform_no_io(구현을 AST 로 읽는다).

3.1 진입점과 프로세스 경계

  • main.py 는 app = create_app() 과 직접 실행용 uvicorn.run() 만 둔다. 직접 실행(uv run python main.py)은 SERVER_HOST·SERVER_PORT·reload=DEBUG·setup_uvicorn_logging() 을 넘긴다. uvicorn main:app CLI 는 CLI 옵션을 따르며 DEBUG=true 만으로 reload 가 켜지지 않는다.
  • 두 경로 모두 정상 ASGI lifespan 을 탄다. --lifespan off 는 Redis 검증·자원 정리를 건너뛰므로 정상 경로가 아니다.
  • reload·다중 worker 는 프로세스마다 import·lifespan 을 다시 수행한다. API worker 마다 Redis client 와 DB pool 이 따로 있고, Celery worker 는 별도 프로세스다.
  • factory 로 만든 이유는 테스트가 격리된 앱(auth 를 뺀 앱, 관리 화면을 끈 앱, 독립 registry 앱)을 만들어 "등록 안 한 앱은 안 붙는다"를 실행으로 증명하기 위해서다.

3.2 설정 로딩

config.py 의 각 BaseSettings 는 env_file=".env", extra="ignore" 로 자기 필드만 해석한다.

  • 우선순위: 프로세스 환경변수 → 작업 디렉터리의 .env → 필드 기본값. .env.example 은 복사용 목록이며 자동 fallback 이 아니다.
  • 리스트 값은 JSON 배열로 준다(예: CORS_ALLOW_ORIGINS=["http://localhost:3000"]). DEBUG=false 는 bool 로 파싱된다.
  • get_*_settings() 는 lru_cache 싱글턴이고, 모듈 끝의 app_settings 등 전역 참조가 import 시 만들어진다. 실행 중 .env 를 바꿔도 반영되지 않는다. 테스트에서 캐시를 비워도 이미 가져간 전역 참조는 바뀌지 않는다.
  • 타입 오류·validator 위반은 config import 자체를 실패시킨다(lifespan 이전).

def create_app(installed_apps=None, registry=None, *, admin_disabled=None) -> FastAPI: ...
  1. 설치 목록 결정(config.INSTALLED_APPS 또는 주입값), registry 결정(전역 apps 또는 주입값)
  2. registry.populate(apps_list) — config → models → ready()
  3. FastAPI(...) 생성 — docs_url=None, redoc_url=None, openapi_url 은 DEBUG 일 때만 /openapi.json, lifespan 연결
  4. CORS → UserInfoMiddleware 등록(나중에 추가한 UserInfo 가 바깥쪽에서 감싼다), 전역 예외 핸들러 5종
  5. install_routers(app, registry)
  6. /health, /ready, DEBUG 일 때만 Scalar /docs
  7. app.state.app_registry 저장, admin_disabled(기본 ADMIN_DISABLED)가 false 면 create_admin(...) — 끈 경우 로그에도 경로를 싣지 않는다

3.4 lifespan 과 자원 관리

lifespan 은 manage_application_resources(app) 를 열고 yield 할 뿐이다. 자원별 코드는 app/core/resources.py 한 곳에 있다.

async with AsyncExitStack() as cleanup:
    cleanup.push_async_callback(_dispose_db_engines)       # 종료 시 3번째
    await cleanup.enter_async_context(_redis(app))         # 종료 시 2번째
    cleanup.push_async_callback(_drain_background_tasks)   # 종료 시 1번째
    await _prepare_database(resources)
    yield resources

Redis 검증 — Redis.from_url(redis_settings.REDIS_URL, socket_connect_timeout=5, socket_timeout=5) 후 ping(). 실패하면 오류 타입만 ERROR 로 남기고 다시 raise 한다 → yield 에 도달하지 않아 서버가 시작되지 않는다. 이어서 ensure_redis_version()(app/core/redis.py)이 INFO server 의 redis_version 을 redis.REDIS_MIN_VERSION(7.0)과 비교해 낮으면 UnsupportedRedisVersion 으로 기동을 멈춘다. 7.0 은 근거가 있는 값이다 — 레이트 리밋이 EXPIRE … NX(7.0)를, refresh 회전이 GETDEL(6.2)을 쓰고 최소 버전은 그 최댓값이다(6.x 서버는 EXPIRE NX 를 문법 오류로 거부해 로그인·가입이 첫 요청부터 500). INFO 를 막아 둔 관리형 Redis·버전을 알려 주지 않는 서버(테스트의 fakeredis 포함)는 WARNING 만 남기고 계속한다. tests/core/test_redis_version.py 가 소스의 명령과 상수를 대조한다. DEBUG 와 무관한 필수 조건이며 끄는 설정은 없다(service-hardening ADR-011). 성공한 client 는 app.state.redis 에 보관되고, 요청 코드는 주입 provider get_redis(request) -> Redis(app/core/redis.py) 하나로 꺼낸다 — lifespan 밖이라 client 가 없으면 ServiceUnavailableException(503). 기능이 Redis.from_url 을 직접 만들지 않는다. 기동 뒤의 도달 가능성은 /ready 가 다시 본다(§3.5). 기동 뒤 Redis 가 사라지면 Redis 를 필수로 쓰는 요청은 503(SERVICE_UNAVAILABLE) 이다(§3.5 예외 표, fail-closed). Redis 를 쓰지 않는 조회(예: 글 목록)는 영향이 없고, 재기동하면 다시 연결된다(연결 풀이 재접속한다 — e2e L5 가 확인).

개발용 테이블 생성 — _prepare_database() 는 create_app() 이 조립에 쓴 registry(app.state.app_registry)를 받아 owned_tables(registry) 로 그 registry 가 소유한 테이블만 센다. 전역 apps 를 따로 읽거나 다시 채우지 않는다.

4. 요청·세션·트랜잭션

4.1 요청 흐름

sequenceDiagram participant C as Client participant M as Middleware participant R as Router participant D as Dependency participant S as Service participant P as Repository participant DB as Database C->>M: HTTP request M->>M: UserInfo 수집 · CORS M->>R: 설치된 route R->>D: get__service(_readonly) D-->>R: Service(session) R->>S: 유스케이스 S->>P: 데이터 접근 P->>DB: SQL / flush opt 쓰기 R->>S: await service.commit() end R-->>C: 응답 DTO M-->>M: 접속 로그 태스크 spawn (별도 풀)
  1. UserInfoMiddleware 가 활성·제외 규칙을 보고 요청 정보를 수집한다. CORS 가 preflight·헤더를 처리한다.
  2. registry 가 설치한 route 가 선택되고 FastAPI 가 path/query/body/form/header 와 Dependency 를 검증·해석한다.
  3. Dependency 그래프: 세션 generator → get_<name>_service → Service(session) → Repository.
  4. 쓰기 핸들러는 업무 후 await service.commit() 을 부르고 응답을 만든다. 조회는 커밋하지 않는다.
  5. 예외로 빠져나가면 세션 컨텍스트(async with)의 close() 가 활성 트랜잭션을 롤백하고 예외는 그대로 재전파되며, 전역 핸들러가 오류 응답을 만든다.
  6. 미들웨어가 응답 상태·소요 시간을 붙여 접속 로그 저장 태스크를 제출한다(§6).

FastAPI 는 한 요청 안에서 같은 Dependency 를 기본 캐시(use_cache=True)한다. writer getter 와 read-only getter 는 서로 다른 callable 이라 같은 세션이 아니다. Service 를 전역 싱글턴으로 두면 세션이 요청을 넘나들므로 금지한다.

DB_MAX_SERVER_CONNECTIONS 를 주면 이 값이 넘칠 때 기동이 실패한다(0 이면 검증하지 않음).

4.4 읽기/쓰기 라우팅

DB_ROUTER_ENABLED=false(기본)면 세션이 writer 엔진에 직접 바인딩되고 바인딩 선택은 쓰이지 않는다. 켜면 RoutingSession.get_bind() 가 구문마다 엔진을 고른다. read-only 세션의 쓰기 차단은 이 설정과 무관하다(아래 "read-only 차단의 범위").

flowchart TD A[구문] --> B{ORM flush 또는 Core DML?} B -- 예 --> W[writer + 이후 sticky] B -- 아니오 --> T{TextClause?} T -- 예 --> I{read 의도가 붙었나?} I -- 아니오 --> W I -- 예 --> P T -- 아니오 --> P{writer 고정 세션?} P -- 예 --> W2[writer] P -- 아니오 --> R[세션에 고정된 replica
없으면 writer]
  • 쓰기 판정 시 세션이 read-only 로 표시돼 있으면 ReadOnlyRoutingError.
  • DB_READ_STICKY_AFTER_WRITE=true(기본)면 쓰기 이후 같은 세션의 SELECT 는 writer 로 간다(read-after-write). 새 요청의 read-only 세션까지 복제 지연을 없애 주지는 않는다.
  • 한 세션은 라운드로빈으로 고른 replica 하나에 고정된다(트랜잭션이 여러 서버로 흩어지지 않도록).
  • replica 장애 → primary 로 한 번 재시도(integration-e2e ADR-010): 읽기 전용 세션의 읽기가 replica 에 연결하지 못하면 (MySQL 2002·2003 접속 불가, 2006·2013·2055 연결 끊김, 1053 종료 중, 3032 offline_mode, 4031 유휴 끊김, 또는 SQLAlchemy 가 연결 무효화로 표시한 오류) 같은 구문을 primary 로 한 번 다시 실행하고 WARNING [DBRouter] replica 연결 오류 — primary 로 다시 읽는다 (<예외 종류>, driver_code=<코드>) 를 남긴다(DSN·메시지는 싣지 않는다). 그 뒤 그 세션은 writer 에 고정된다. 쿼리 자체의 오류(문법·제약·없는 테이블)는 재시도하지 않는다. 쓰기와 섞일 수 있는 일반(라우팅) 세션도 재시도하지 않는다. primary 도 실패하면 그 오류가 그대로 올라간다. replica 가 없는 구성은 동작 변화가 없다. /ready 는 그대로 writer 만 본다.
  • DB_REPLICATION_ENABLED=true 는 DB_ROUTER_ENABLED=true 와 MYSQL_REPLICA_HOSTS 를 요구한다. replica 계정·DB 를 비우면 primary 값을 재사용한다. replica 없이 라우터만 켜면 읽기도 writer 로 간다.
  • 복제 지연을 허용할 수 없는 읽기는 using_writer(session) 으로 writer 에 고정한다.
  • 기동 시 db_settings.describe_routing() 이 비밀번호를 가린 DSN(URL.render_as_string(hide_password=True))으로 구성을 한 줄 남긴다.

text() 는 SQL 을 해석하지 않는다. 첫 단어 파싱은 WITH doomed AS (SELECT ...) DELETE ... 같은 CTE DML 을 읽기로 오판해 replica 로 보낸다. 그래서 호출부가 의도를 붙이고(read_intent·write_intent, 조회는 statement_intent), 의도가 없는 TextClause 는 쓰기로 본다(fail-closed). RawRepositoryBase 를 쓰면 메서드가 의도를 자동으로 붙인다.

read-only 차단의 범위

경로 차단
ORM flush Session 에 전역 등록된 before_flush 리스너가 거부 — 라우터 설정·sessionmaker 종류와 무관
Core DML·임의 session.execute() do_orm_execute 리스너가 실행 전에 판정 — 잠금 없는 Select 와 read_intent() 가 붙은 text() 만 통과하고 나머지는 거부(default-deny). ORM with_for_update() 는 쓰기로 보고 거부하며, 라우터는 writer 로 보낸다
Raw 쓰기(execute, for_update=True) 위 리스너에 더해 RawCRUDBase 가 is_read_only_session() 으로 먼저 거부 — 어느 메서드가 원인인지 메시지에 남는다

판정은 구문 타입과 의도 태그만 본다 — SQL 문자열을 해석하지 않으므로 완전한 sandbox 가 아니다. 위 세 경로의 차단은 라우터 on/off 두 구성에서 tests/core/test_read_only_guard.py 가 고정하고, 조회 경로가 쓰지 않는다는 규칙은 tests/test_read_path_no_commit.py 가 구조로 함께 고정한다.

read-only 표시는 DB 권한을 대체하지 않는다. 운영에서는 replica 전용 읽기 계정을 함께 쓴다.

4.5 트랜잭션 경계

  • 커밋은 쓰기 핸들러 본문이 응답 생성 전에 한 번. Repository·Service·Dependency 는 스스로 커밋하지 않는다.
  • 순서는 response = XResponse.model_validate(obj) → await service.commit() → return response 하나다. 응답 DTO 검증이 실패하면 커밋 없이 500 으로 끝나고 세션 Dependency 가 rollback 한다(tests/test_validate_before_commit.py).
  • 예외로 빠져나가면 세션 Dependency 가 rollback 한다. 이미 커밋한 뒤의 실패는 되돌리지 않는다.
  • 여러 Service 를 한 원자 단위로 묶으려면 같은 writer 세션을 주입하고 마지막에 한 번 커밋한다.
  • BaseService.commit() 은 커밋 시점의 SQLAlchemyError(지연 제약, 연결 유실 등)도 convert_db_error() 로 바꾼다.
  • 요청 밖에서는 background_session() 을 열고 직접 커밋한다 — 성공 시 자동 커밋하지 않는다.

왜 Dependency 가 아니라 핸들러인가. 예전에는 Dependency 가 yield 뒤에서 커밋했다. 기본 request scope 의 yield dependency 종료 코드는 응답 전송 후 실행되므로(FastAPI 0.141 에서 실측), 커밋이 실패해도 클라이언트는 이미 201 을 받는다. function scope 는 종료 시점이 다르지만 (FastAPI 문서), 이 프로젝트는 커밋을 teardown 에 맡기지 않는다. 회귀 가드: tests/test_read_path_no_commit.py, 기능별 test_transaction_boundary.py.

DB 커밋과 HTTP 전송은 하나의 원자적 트랜잭션이 아니다. 커밋 후 연결이 끊길 수 있으므로 중요한 생성 업무는 멱등 키 정책을 요구사항으로 정한다.

4.7 DB 오류 변환

SQLAlchemy 예외의 문자열에는 실행 SQL·바인딩 값·때로 DSN 이 들어 있다. convert_db_error() 는 경계에서 한 번 변환하며 예외 클래스명·드라이버 코드·모델·연산만 로그에 남기고, 호출부는 raise ... from None 으로 원본을 끊는다.

4.8 모델과 기능 카탈로그

모델은 Base 에 필요한 Mixin 을 조합한다. sort_order 로 컬럼 순서(id → 도메인 → created_at → updated_at)를 고정해 create_all 과 migration 의 결과가 갈리지 않게 한다. 시각은 DB 가 아니라 앱이 timezone_settings.utc_now()(aware UTC)로 채운다. Mapped[datetime] 은 app/core/models/types.py 의 UTCDateTime 이다 — MySQL DATETIME(6)·UTC 로 저장하고, naive datetime 은 저장 경계에서 ValueError 로 거부하며, 읽을 때 tzinfo=UTC 를 붙여 응답이 Z 오프셋을 갖는다. Raw SQL 은 bindparam(..., type_=UTCDateTime()) 로 같은 변환을 태운다. 지역 시각(TIME_ZONE)은 표시·집계 경계에서만 쓴다 — 리포트·접속 로그의 날짜 범위는 지역 일자를 UTC 순간으로 바꿔 조회한다(service-hardening ADR-010). UpdatedAtMixin.onupdate 는 ORM UPDATE 에만 적용된다.

여러 프로세스 주의 — 한 파일은 한 프로세스만 회전시킬 수 있다. uvicorn --workers 2 이상·Celery prefork(--concurrency > 1 의 자식 프로세스)는 같은 파일을 여러 프로세스가 회전시켜 안전하지 않다. 그 배포는 콘솔(stdout) + 수집기/logrotate, 파일 로그 끔 (LOG_FILE_ENABLED=false)으로 운영한다. 기동 시 감지하지는 않는다(워커 수를 앱이 믿을 만하게 알 방법이 없다 — 문서로만 안내). - 헤더(app=) — filters._app_from_path() 한 함수가 정한다. 우리 코드는 소스 경로(<기능명>·core·celery·utils·migrations·app), 저장소 밖 코드는 로거 이름 표(celery.*·kombu.* → celery, uvicorn.* → uvicorn, sqlalchemy.* → sqlalchemy, alembic.* → alembic, 그 밖 → ext). 새 기능은 아무것도 하지 않아도 자기 이름의 헤더가 붙는다. - 앱별 레벨 — LOG_APP_LEVELS="blog=DEBUG,sqlalchemy=WARNING". 키는 헤더 이름, 지정 없는 헤더는 LOG_LEVEL. 구현은 필터 하나 (AppLevelFilter, 모든 핸들러에서 ContextFilter 바로 뒤)이고 root 레벨은 전체 최솟값으로 내려 레코드가 필터까지 오게 한다. 형식·레벨이 틀리면 설정 로드가 실패하고, 모르는 헤더는 WARNING 한 줄만 남긴다. 핸들러는 여전히 root 에만 붙는다(앱별 로거 등록 없음, ADR-019). - 포맷: console 은 LOG_CONSOLE_FORMAT, 파일은 LOG_FILE_FORMAT, 시각은 LOG_DATE_FORMAT(development 는 뒤에 .밀리초). 기본값은 [{asctime} {tzname}] {levelname:5} [app={appname}] [{module}:{classname}:{funcName}:{lineno}] {message} / %Y-%m-%d %H:%M:%S (config.DEFAULT_LOG_FORMAT = app.utils.logs.LOG_FORMAT). 설정 로드 때 샘플 레코드로 한 번 렌더해 모르는 필드·괄호 불일치면 기동을 멈추고, 필수 필드 {asctime}·{levelname}·{appname}·{module}·{classname}·{funcName}·{message} 가 하나라도 없어도 멈춘다(config.REQUIRED_LOG_FIELDS). - SqlNoiseFilter 가 모든 핸들러에서 SQLAlchemy·드라이버 로거의 SQL 본문·바인딩 값을 막는다. LOG_SQL_ECHO_ENABLED=true 로만 열 수 있고, production/staging 에서는 설정 로드가 거부한다. - 비밀값 가리기 — app/utils/logs/redaction.py 의 SecretRedactor 가 규칙의 정본이다(DSN·URL 의 계정명과 비밀번호 scheme://***:***@host — 계정명 없는 scheme://:***@host·계정명만 있는 scheme://***@host, 비밀번호는 마지막 @ 까지, password·secret·token·api_key·authorization 으로 끝나는 키의 값, Bearer 토큰, JWT → ***). 여기에 config.LOG_REDACTED_SETTINGS(DB writer·replica 계정명·비밀번호, Redis 비밀번호, JWT access/refresh 키, SESSION_SECRET_KEY)의 현재 값 원문을 configure_logging() 이 넘겨, 로그 어디에 나와도 *** 로 바꾼다. 4글자 미만 값(주로 짧은 계정명)은 일반 단어와 겹치므로 user=·username= 뒤와 DSN 에서만 가린다. 새 비밀 설정은 이 목록에 넣어야 한다(test_every_secret_setting_is_redacted_from_logs 가 이름 규칙으로 강제). 가리기는 LogRecord factory 에 걸려 렌더된 메시지·traceback 본문(exc_text 로 미리 포맷해 고정)·stack_info 를 레코드가 만들어질 때 가린다 — 우리가 포매터를 소유하지 않는 경로도 같은 규칙을 탄다. 예외 타입·체인·파일·줄은 남는다. 접속 로그(DB 저장)는 대상이 아니다(§6). - 세션 롤백 로그(app/core/db/session.py)는 ERROR 에 예외 타입과 소요시간만 남긴다 — DB 예외의 str() 에 실행된 SQL 과 바인딩 값이 들어 있고, 앱 로거 이름은 SqlNoiseFilter 를 통과하기 때문이다. 추적이 필요하면 DEBUG 레벨에서 같은 지점의 exc_info=True 상세 레코드가 트레이스백 전문을 남긴다. 그래서 production/staging 은 debug 모드 자체를 거부한다(§3.2). - Service 는 LoggerMixin 을 상속해 self.log 를 쓴다. 키 표·Django LOGGING 설정 대응표는 README "로깅" 절이 정본이다.

  • 저장 실패는 로그만 남기고 응답에 영향을 주지 않는다. 태스크 제출은 call_next 가 응답을 돌려준 뒤이며, 클라이언트가 모든 바이트를 받았다는 보증은 아니다. call_next 가 처리되지 않은 예외로 끝나면 response_status=500 으로 기록한 뒤 예외를 그대로 다시 던진다.
  • best-effort 다. 감사 목적의 필수 데이터라면 durable queue 로 바꿔야 한다. 중요한 업무 저장을 이 runner 에 넣지 않는다.

보존 기간 삭제 (security-ops-hardening ADR-002·ADR-003): home 의 Celery 태스크 home.purge_expired_access_logs 가 UserAccessLogService.purge_expired() 를 부른다. 기준은 now(UTC) - ACCESS_LOG_RETENTION_DAYS 일 이고 그보다 오래된 행만 지운다 (정확히 그 순간의 행은 남는다). UserAccessLogRepository.delete_created_before() 가 오래된 순으로 id 를 최대 5,000개(user_access_log_service.PURGE_BATCH_SIZE) 고른 뒤 그 id 로 지우고, 서비스가 배치마다 커밋한다 — 긴 잠금·거대 트랜잭션을 피한다. 두 구문으로 나눈 이유는 MySQL 이 같은 테이블의 IN (SELECT … LIMIT) 을 거부하고 SQLite 는 DELETE … LIMIT 을 받지 않기 때문이다(두 DB 에서 같은 쿼리). 보존 0 이면 DB 에 가지 않는다. 일정은 매일 03:30(TIME_ZONE)이고 home 의 tasks.py 가 celery_app.add_periodic_task 로 등록한다(§9).

클라이언트 IP (app/core/middlewares/client_ip.py 의 ClientIPResolver, setup_user_info_middleware() 가 설정으로 한 번 만들어 미들웨어에 주입): TRUSTED_PROXY_HOPS=0 이면 소켓 주소(request.client.host)만 쓴다. N 이면 X-Forwarded-For 목록 끝에 소켓 주소를 붙이고, 소켓 주소를 0번째로 센 오른쪽 N번째(= XFF 의 오른쪽 N번째, 가장 바깥 신뢰 프록시가 본 주소)를 쓴다. 그보다 왼쪽은 클라이언트가 쓴 값이라 믿지 않는다. 체인이 N보다 짧거나 값이 IP 가 아니면(ipaddress.ip_address 실패) 소켓 주소로 돌아간다. X-Real-IP 는 N>0 이고 XFF 가 없을 때만 본다. 기본값 0 은 이전 동작(XFF 첫 값을 무조건 신뢰)을 바꾼 것이다 — 프록시 뒤에 배포하면 홉 수를 설정해야 실제 클라이언트 IP 가 기록된다(service-hardening ADR-005).

저장 전 정리: query string 의 민감 키 값은 *** 로 바뀐다. 문자열은 home 기능의 UserAccessLogService.create_access_log 가 모델 컬럼 길이(UserAccessLog.__table__ 의 String(n))로 자른다 — 긴 헤더·쿠키 하나로 MySQL strict 모드의 1406 이 나서 기록이 빠지던 경로를 막는다(service-hardening ADR-006).

수집 필드 (user_access_logs): ip_address(위 ClientIPResolver), forwarded_for, real_ip(헤더 원문 — 위조 가능), user_agent 와 파싱 결과(os_name·os_version·browser_name·browser_version·device_type·device_brand·device_model·is_bot), request_path, request_method, query_string(민감 키 값 ***), referer, accept_language, session_id(SESSION_COOKIE_NAME 쿠키 원문), user_id(request.state), response_status, response_time_ms. 인덱스: created_at·ip_address·os_name·browser_name·device_type·country·session_id·user_id.

조회 API(/api/v1/home/access-logs 외 4개)는 모두 read-only 세션을 쓰며 슈퍼유저 전용이다(라우터 의존성 require_superuser, §7.1). 인증된 요청의 user_id 는 get_current_principal 이 핸들러 실행 중에 request.state.user_id 로 채우고, 미들웨어가 응답 뒤에 읽어 기록한다.

7. 인증 (JWT)

OAuth2 password flow + JWT access/refresh(회전). 자격증명은 user 기능의 User.hashed_password 에 있고, auth 는 인증 로직만 담당한다(auth → user 의존은 의도된 예외). 목적마다 클래스 하나인 보안 부품은 app/core/security/ 에 있다 — user 기능(해시)과 다른 기능의 인증 의존성(토큰 검증)도 써야 하므로 core 에 둔다.

부품 위치 역할
PasswordHasher app/core/security/passwords.py pwdlib Argon2 해시. 기존 bcrypt($2…)는 이전 규칙(72바이트 절단)으로 검증하고 성공하면 Argon2 새 해시를 돌려준다. 타이밍 균등화 더미 해시도 Argon2
TokenService app/core/security/tokens.py PyJWT 발급·검증. claims sub·type·iat·nbf·exp·jti·iss·aud + access username·su(슈퍼유저 여부, bool 필수) / refresh fam. 실패는 원인과 무관하게 InvalidTokenException(401, 오류 코드 AUTH_INVALID_TOKEN)
RefreshTokenStore app/core/security/refresh_store.py Redis 에 미사용 refresh(auth:rt:{jti})·사용자 family 집합·family 폐기 표시를 둔다. 소비는 Redis GETDEL 하나
RateLimiter app/core/security/rate_limit.py Redis 고정 창(MULTI 안에서 INCR + EXPIRE NX + TTL). 초과는 TooManyRequestsException(429, Retry-After)
Principal · OwnershipPolicy app/core/security/principal.py 요청 주체(id·username·is_superuser, 불변)와 소유권 판정 ensure_can_modify(owner_id, principal) — 소유자 또는 슈퍼유저, 아니면 403

조립은 provider 함수가 한다(생성자 주입, service-hardening ADR-022). 여러 기능이 함께 쓰는 provider — get_password_hasher·get_token_service·get_ownership_policy(프로세스당 하나, lru_cache)와 get_refresh_token_store(Depends(get_redis), §3.4) — 는 app/core/security/dependencies.py 에 있고, 인증 기능(app/features/auth/dependencies/auth_dependencies.py)은 그것을 그대로 쓰면서 get_client_ip_resolver·get_rate_limiter·get_auth_service(session, hasher, tokens, store) 를 더한다.

메서드 경로 인증 요청 성공 실패
POST /api/v1/auth/register — JSON (비밀번호 8~128자) 201 409 사용자명 중복 · 422 · 429
POST /api/v1/auth/login — form (username·password) 200 401 · 422 · 429
POST /api/v1/auth/refresh — JSON {"refresh_token": ...} 200 401 무효·만료·재사용·폐기·비활성 · 422
POST /api/v1/auth/logout — JSON {"refresh_token": ...} 204 401 무효·만료 · 422

토큰 응답은 {"access_token", "refresh_token", "token_type": "bearer", "expires_in": <access 수명 초>} 다.

흐름

  1. login — login_rate_limit 의존성이 ip(AUTH_LOGIN_IP_MAX_ATTEMPTS)와 ip+소문자 username(AUTH_LOGIN_MAX_ATTEMPTS)을 AUTH_LOGIN_WINDOW_SECONDS 창으로 센다. ip 는 접속 로그와 같은 ClientIPResolver(TRUSTED_PROXY_HOPS, §6)로 정한다. AuthService.authenticate(/admin 로그인과 같은 verify_credentials)가 해시기를 asyncio.to_thread 로 부르고, bcrypt → Argon2 재해시가 있으면 UserRepository.update 로 flush 해 둔다. 새 family 로 토큰 쌍을 발급하고 refresh 의 jti 를 기록한 뒤 핸들러가 커밋하고 ip+username 카운터를 지운다.
  2. refresh — refresh 토큰을 검증하고 GETDEL auth:rt:{jti} 로 소비한다. 값이 없으면 이미 쓴 토큰의 재사용(탈취 신호)이라 그 family 를 폐기하고 401 — 정상 사용자가 가진 같은 family 의 최신 토큰도 함께 죽는다. family 가 폐기됐거나 사용자가 없거나 비활성이면 401(비활성·부재는 family 도 폐기). 통과하면 같은 family 로 새 쌍을 발급한다.
  3. logout — refresh 토큰의 family 를 폐기하고 jti 를 소비한다(멱등, 204). access 토큰은 만료(ACCESS_TOKEN_EXPIRE_MINUTES)까지 유효하다 — 즉시 폐기 목록은 두지 않고 짧은 수명으로 대신한다.
  4. /me — get_current_principal(아래 §7.1) → read-only 세션을 primary 에 고정(using_writer)한 UserRepository.get_by_id → 없거나 비활성이면 401. replica 에서 읽으면 복제 지연 중 가입 직후의 유효한 토큰이 401 이 되고 비활성화·삭제가 늦게 반영된다(e2e-policy-2 결정 5, integration-e2e F-008). 다른 읽기 라우팅은 그대로다. Redis 도 쓰기 세션도 쓰지 않는다.
  5. register — register_rate_limit(ip, AUTH_REGISTER_MAX_ATTEMPTS/AUTH_REGISTER_WINDOW_SECONDS) 뒤 Argon2 해시로 저장, 응답 DTO 검증 후 커밋.

access·refresh 수명(ACCESS_TOKEN_EXPIRE_MINUTES·REFRESH_TOKEN_EXPIRE_DAYS)은 README 세션·토큰 만료 표에 있다.

7.1 인가 — 주체·소유권·슈퍼유저

권한은 슈퍼유저/일반 2단계다(users.is_superuser). 인가는 core 의 주입 경로 하나(app/core/security/dependencies.py)로 한다 — 기능이 인가를 위해 user 기능을 import 하지 않는다(service-hardening C-11).

8. 관리 화면 (SQLAdmin)

설계·흐름도·쿠키 구조·위협 모델·문제 해결은 관리 화면 인증 가이드에 있다. 여기는 요약이다.

  • ADMIN_DISABLED=false(기본)일 때만 create_admin() 이 /admin 을 마운트하고 설치 앱의 admin_views 를 등록한다. DEBUG 와 독립이다. ADMIN_DISABLED=true 면 마운트·sqladmin import·세션 미들웨어·인증 백엔드가 모두 없고, 앱의 어떤 응답에도 /admin 이 나오지 않는다 (tests/core/test_admin_disabled.py). 예전 ADMIN 설정이 남아 있으면 기동이 멈춘다(§3.2).
  • ModelView 는 모델과 같은 기능 폴더의 admin.py 가 소유한다(중앙 취합 파일 없음). 모델이 있는 앱은 admin.py 를 가져야 한다(tests/core/test_admin_wiring.py). User 의 hashed_password 는 목록·상세·폼·내보내기 어디에도 나오지 않고 User 생성은 막혀 있다(tests/core/test_admin_views.py).
  • 활성 슈퍼유저 로그인이 필요하다. AdminAuthBackend(app/core/security/admin_auth.py)가 SQLAdmin AuthenticationBackend 를 구현한다.
  • 로그인: 폼 username/password/csrf_token → CSRF 토큰 확인(AdminCsrfMiddleware — 아래, 없거나 다르면 403 으로 로그인 화면을 다시 그리고 레이트 리밋·자격 확인을 하지 않는다) → 레이트 리밋(AUTH_LOGIN_* 한도 재사용, 키 접두사 admin-login: 으로 API 와 분리, ip·ip+username) → 자격 확인 → 활성·슈퍼유저면 request.session.clear() 후 사용자 id 저장 + 새 CSRF 토큰 + RedisSessionMiddleware.rotate()(응답 직전 새 세션 ID 발급, 이전 Redis 키 삭제 — 세션 고정 방지). 실패는 사유 없이 400, 한도 초과는 로그인 화면을 429 + Retry-After 로 다시 그린다.
  • 매 요청: 세션의 id 로 DB 를 다시 확인해 활성·슈퍼유저가 아니면 세션을 비우고 로그인 화면으로 보낸다(아래 즉시 폐기와 이중 방어).
  • 로그아웃: POST 전용(require_post_logout 이 sqladmin 의 GET /admin/logout 라우트를 POST 라우트로 바꾼다 — GET 은 405) + CSRF 토큰. 세션을 비우면 미들웨어가 Redis 키를 지우고 쿠키를 지운다 — 복사해 둔 쿠키도 그 순간 무효다.
  • 자격 확인은 core 가 사용자 모델을 모르므로 AuthConfig.ready() 가 app/core/security/admin_credentials.py 의 훅에 등록한 UserAdminCredentials(app/features/auth/admin_credentials.py, background_session + PasswordHasher, API 로그인과 같은 verify_credentials)가 한다. 등록한 앱이 없으면 관리 화면을 열지 않고 기동을 멈춘다.
  • 세션은 Redis 서버 세션이다(app/core/security/admin_session.py, admin-session-hardening ADR-001). 쿠키 admin_session 에는 secrets.token_urlsafe(32) 세션 ID 만 있고(path /admin, SameSite=Strict, HttpOnly, staging/production 에서 Secure, Max-Age = 절대 만료), 내용은 Redis 에 있다.
  • AdminSessionStore 가 저장·조회·삭제·사용자별 폐기를, ASGI RedisSessionMiddleware 가 scope["session"] 에 dict 를 채우고 응답 직전에 저장·회전·삭제한다 (request.session 인터페이스 그대로).
  • Redis 키 admin:sess:{HMAC-SHA256(SESSION_SECRET_KEY, 세션 ID)} → JSON {"data", "user_id", "created_at"}. TTL = min(미사용 만료, 절대 만료까지 남은 초), 요청마다 다시 건다(내용이 바뀌면 SET, 아니면 EXPIRE). 사용자별 인덱스 admin:user_sessions:{user_id}(SET, TTL = 절대 만료).
  • 만료: 절대 ADMIN_SESSION_MAX_AGE_SECONDS(기본 8시간, 연장 불가 — 읽을 때 created_at 으로도 검사), 미사용 ADMIN_SESSION_IDLE_SECONDS(기본 30분). 쿠키의 ID 가 Redis 에 없으면(만료·폐기·위조) 빈 세션이고 쿠키를 지운다(Max-Age=0).
  • SESSION_SECRET_KEY 는 세션 ID → Redis 키 HMAC 키다 — Redis 키가 새도 쿠키를 만들 수 없고, 키를 바꾸면 모든 관리 세션이 무효다.
  • Redis 장애는 fail-closed: 세션을 읽지 못하면(lifespan 밖이라 클라이언트가 없는 경우 포함) 관리 화면은 503 이고 앱에 닿지 않는다. 응답 직전 저장 실패(쿠키 없는 첫 요청의 세션 생성 등)도 앱이 만든 응답 대신 같은 503 이다 — 응답 시작 전이라 바꿀 수 있다(e2e-policy-2 결정 6).
  • 미들웨어 순서는 RedisSessionMiddleware(바깥) → AdminCsrfMiddleware(안쪽)이고 SQLAdmin 하위 앱에만 있다 — 메인 앱에는 세션 미들웨어가 없고 API 인증(JWT Bearer)은 세션을 보지 않는다(tests/core/test_admin_login_flow.py).
  • 즉시 폐기(ADR-005·ADR-008·ADR-010): 판정 한 곳 — revocation_for_change(before, changes)(app/core/security/revocation.py)가 변경 전 값과 비교해 Revocation(admin_sessions, refresh) 를 돌려주고, 삭제는 revocation.REVOKE_ON_DELETE, 비밀번호 변경 스크립트는 revocation.REVOKE_ON_PASSWORD_CHANGE(둘 다 두 집합 모두)다. UserSessionRevoker.revoke(user_id, revocation) 는 판정대로 refresh family(RefreshTokenStore.revoke_user)·관리 세션(AdminSessionStore.revoke_user)을 지운다.

지금은 두 집합이 같지만 판정은 두 집합을 따로 돌려준다 — 한쪽만 바꿀 일이 생겨도 조건은 이 함수 한 곳에만 있다. 원칙은 관리 화면 경로 = API 경로(UserService)다.

  • API: UserService(app/features/user/services/user_service.py)가 수정·삭제 때 판정해 부른다. 생성자는 revoker 하나를 받고, provider 는 get_user_session_revoker(app/core/security/dependencies.py)다. 관리 화면이 꺼져 있으면 관리 세션 저장소가 None 이라 refresh 쪽만 지운다.
  • 관리 화면: UserAdmin(app/features/user/admin.py)의 커밋 전 훅이 같은 판정으로 revoker_from_scope(request.scope) 를 부른다 — on_model_change (생성 제외)·on_model_delete(revocation.REVOKE_ON_DELETE). 자기 자신을 강등·비활성화하면 현재 세션도 지워져 다음 요청에서 로그인 화면이 나온다(의도).
  • 폐기는 커밋 전이다(fail-closed): sqladmin 0.32 의 _queries._update_async·_delete_async 가 on_* 훅을 세션 안에서 커밋 전에 부르고, API 는 핸들러가 나중에 커밋한다. Redis 폐기가 실패하면 예외가 커밋을 막는다 — 관리 화면 수정은 400 오류 화면 + DB 변경 없음, 삭제는 목록 error= + 행 유지. 반대로 폐기 뒤 커밋이 다른 이유로 실패하면 세션만 지워진다(다시 로그인하면 된다). 폐기와 커밋 사이에 다시 로그인한 세션은 매 요청 DB 확인이 막는다(R-005).
  • 스크립트: scripts/create_superuser.py --set-password 는 별도 프로세스라 커밋 뒤 revoke_sessions_in_redis 로 관리 세션과 refresh 를 지운다 (revocation.REVOKE_ON_PASSWORD_CHANGE). Redis 실패면 종료 코드 1(비밀번호는 바뀌었지만 세션을 지우지 못했습니다)이다.
  • CSRF(ADR-002): AdminCsrfMiddleware(app/core/security/admin_auth.py)가 /admin 아래 POST·PUT·PATCH·DELETE 전부(로그인 포함 — 검사는 여기 하나)에서 헤더 X-CSRF-Token, 없으면 폼 필드 csrf_token 을 세션 토큰(AdminCsrf)과 hmac.compare_digest 로 비교한다. 폼은 본문을 한 번 버퍼링해 파싱하고 같은 본문을 다운스트림에 다시 흘려 준다. 버퍼링 상한은 10 MiB(admin_auth.py 의 상수 — 설정이 아니다) — Content-Length 로 먼저, 없거나 거짓이면 읽는 도중 누적 크기로 판정해 413, 필드 하나가 1 MiB 를 넘으면 400 이다(500·연결 끊김 없음, e2e-policy-2 결정 7). 실패는 403 이다 — 로그인은 로그인 화면, 로그인한 세션은 관리 화면 error.html, 로그인 전 요청은 문구만. 로그는 WARNING [AdminCsrf] 토큰 불일치 METHOD PATH. 레이트 리밋·자격 확인보다 먼저라 위조 요청이 카운터를 올리지 못한다.
  • 로그인 화면은 app/templates/admin/sqladmin/login.html(Bootstrap 5.3.8 CSS, SRI)이 sqladmin 기본 템플릿을 덮어쓴다 — templates_dir 의 로더가 패키지 템플릿보다 먼저다. 폼은 csrf_token(request)(백엔드가 템플릿에 건 전역 함수 — 세션에 토큰이 없으면 secrets.token_urlsafe(32) 로 만든다)를 hidden 입력으로 싣는다. 로그인 이후 화면은 app/templates/admin/sqladmin/base.html 이 sqladmin 원본(sqladmin_original/base.html)을 확장해 <meta name="csrf-token"> 을 싣고, 인라인 스크립트가 같은 출처 POST 폼(생성·수정)에 hidden csrf_token 을, 같은 출처 XHR·fetch(삭제·일괄 삭제·가져오기)에 X-CSRF-Token 을 붙이며, 로그아웃 링크 클릭을 토큰 실은 POST 폼 제출로 바꾼다. JS 가 꺼져 있으면 로그아웃은 405 다. 원본 대조 테스트(tests/core/test_admin_csrf.py)가 sqladmin 업그레이드로 원본 블록·로그아웃 링크·main.js 요청 방식·로그아웃 라우트가 바뀌면 실패한다. 사용자 정의 @action(GET)은 보호 밖이다(이 저장소는 안 쓴다).
  • 목록의 시각 컬럼 필터는 LocalDateFilter(app/core/admin_filters.py)다. sqladmin 의 연산 필터는 UTCDateTime 을 날짜로 알아보지 못해 문자열을 바인딩하고 목록이 500 이 된다. 이 필터는 YYYY-MM-DD 를 TIME_ZONE 의 날짜로 읽어 지역 0시를 UTC 순간으로 바꾼 범위로 거른다 — 같은 날 [D, D+1)·이후(포함) >= D·이전(미포함) < D·기간 S~E(양 끝 포함 [S, E+1), 한쪽만이면 열린 구간), 빠른 선택(오늘·최근 7일·최근 30일 — 최근 N일은 오늘을 포함한 기간). 화면은 시작일·종료일 날짜 입력 둘을 제출 직전 스크립트가 값 하나로 합친다(app/templates/admin/sqladmin/filters/local_date_filter.html). 형식이 틀리거나 역순이면 필터 없이 목록을 보여 준다(WARNING [admin] 날짜 필터 기간 무시). created_at 이 있는 모든 ModelView 가 단다(tests/core/test_admin_pages.py).
  • 기본이 "켜짐" 인 것은 받자마자 DB 를 들여다보게 하려는 개발 우선 결정(2026-08-12)이다. 배포 환경에서도 켤 수 있다(로그인이 막는다).

    registry = Apps()
    registry.populate(installed_apps, run_ready=False)
    return registry.task_modules()                   # 앱별 <앱>.tasks 중 존재하는 것

celery_app = Celery("project", broker=redis_settings.REDIS_URL, backend=redis_settings.REDIS_URL,
                    include=discover_task_modules(INSTALLED_APPS))
# JSON serializer 만 허용, task_track_started, enable_utc=True, timezone=TIME_ZONE(일정 해석용), beat_schedule={}
  • 태스크는 기능 폴더의 tasks.py(선택, AppConfig.tasks_module)에 @celery_app.task 로 정의한다. 예: app/features/home/tasks.py 의 home.aggregate_access_stats — background_session() 으로 세션을 열고, 서비스는 HTTP 경로와 같은 home provider build_user_access_log_service(session) 로 조립한다(service-hardening ADR-012).
  • 워커 include 는 config.INSTALLED_APPS 로 만든다. app/celery 는 어떤 기능도 import 하지 않는다(tests/test_layering_and_openapi.py::test_celery_does_not_depend_on_features). 목록에서 앱을 빼면 그 앱의 태스크·모델도 워커에서 빠진다. 같은 registry 가 2단계(models)까지 돌므로 워커에서도 모든 설치 앱의 mapper 가 등록된다. ready() 는 돌리지 않는다 — 접속 로그 sink 결선은 API 프로세스 전용이다.
  • 발견은 importlib.util.find_spec 으로 존재만 본다. 태스크 module 은 celery_app 을 import 하므로, 발견 단계에서 import 하면 순환 import 다. 태스크 module 내부의 import 오류는 워커가 include 를 import 할 때 드러난다.
  • 동기 태스크 안의 코루틴은 app/celery/task.py 의 run_async() 가 worker 프로세스당 영속 event loop 에서 실행한다.
  • worker 종료: app/celery/lifecycle.py 가 worker_process_shutdown 신호에서 살아 있는 loop 로 dispose_engine() → shutdown_asyncgens() → loop close → 전역 참조 해제.
  • 주기 실행(beat): 일정도 기능의 tasks.py 가 celery_app.add_periodic_task(...) 로 등록한다 — beat 는 기동 때 워커와 같은 include 로 태스크 module 을 불러온 뒤 beat_schedule 을 읽으므로, 중앙 Celery 앱은 기능을 import 하지 않는다. 현재 일정은 home 의 home.purge_expired_access_logs(매일 03:30, timezone=TIME_ZONE 기준) 하나다. 실행: uv run celery -A app.celery.app beat --loglevel=info (worker 와 별도 프로세스, 한 개만 — 여러 개면 같은 일정이 중복 실행된다).
  • API 기동은 worker·beat 를 띄우지 않고, API lifespan 은 worker 의 broker 연결·loop 를 정리하지 않는다(소유권이 다른 프로세스).
  • 태스크에는 살아 있는 세션·Service·Request 를 넘기지 말고 JSON 직렬화 가능한 id·값만 넘긴다. 재시도·멱등 정책은 태스크별로 정한다.

11.1 배포 체크리스트 — 사람이 확인할 것

# 확인 빠뜨리면
1 DEBUG=false (그리고 LOG_LEVEL 을 DEBUG 로 두지 않는다) /docs·/openapi.json 공개, 시작 시 create_all 실행으로 스키마 관리 주체가 둘로 갈린다. production/staging 에서는 기동이 거부된다(§3.2)
2 관리 화면을 쓰지 않으면 ADMIN_DISABLED=true. 쓴다면 HTTPS 로만 접근(staging/production 쿠키는 Secure) 켜 둔 /admin 은 로그인 화면을 공개한다(로그인은 필요하다). 예전 ADMIN 줄이 남아 있으면 기동이 멈춘다
3 외부 노출이 필요 없으면 SERVER_HOST=127.0.0.1 기본 0.0.0.0 — 앱은 이 조합을 막지 않는다. 관리 화면을 내부망으로만 쓰려면 프록시에서 /admin 을 제한한다
4 비밀값 교체: ACCESS_TOKEN_SECRET_KEY·REFRESH_TOKEN_SECRET_KEY·SESSION_SECRET_KEY(서로 다른 secrets.token_urlsafe(48) 값, 세션 키는 /admin 세션 ID → Redis 키 HMAC)·MYSQL_PASSWORD·REDIS_PASSWORD 세 비밀키가 placeholder 이거나 access·refresh 가 같으면 기동이 거부된다. DB·Redis 비밀번호는 앱이 검사하지 않는다 — 기본 자격증명 노출
5 CORS 는 실제 frontend origin 만 CORS_ALLOW_ORIGINS=["*"] 와 CORS_ALLOW_CREDENTIALS=true 조합은 설정 로드가 거부한다
6 Redis 는 7.0 이상, 인증·사설망 startup 필수 자원이자 Celery broker·/admin 세션 저장소(Redis 를 쓸 수 없으면 관리 화면은 503). 7.0 미만이면 기동이 거부된다(EXPIRE NX). INFO 를 막은 관리형 Redis 는 확인을 건너뛰므로 버전을 직접 확인한다
7 DB_WORKER_PROCESSES·DB_MAX_SERVER_CONNECTIONS 를 실제 값으로 트래픽이 몰릴 때만 "Too many connections" 로 드러난다
8 오케스트레이터가 /health 를 liveness, /ready 를 readiness 로 연결 DB 흔들림에 프로세스 재시작
9 로그 보존·회전 정책과 민감값(Authorization·JWT·비밀번호·자격증명·과도한 요청 본문) 비기록 —
10 프록시 뒤 배포면 TRUSTED_PROXY_HOPS 를 앞단 프록시 단 수로 0 으로 두면 모든 클라이언트가 프록시 IP 하나로 보여 접속 로그와 로그인 레이트 리밋(API·/admin)이 전체 사용자를 한 사람으로 취급한다(한 사람이 한도를 채우면 전원이 429). 크게 잡으면 위조된 X-Forwarded-For 를 믿어 IP 위조가 가능하다(service-hardening R-013)
11 첫 관리자를 scripts/create_superuser.py 로 만들고(대화형 또는 --password-stdin), 관리 API 가 일반 토큰에 403 인지 확인 슈퍼유저가 없으면 관리 API 도 /admin 로그인도 쓸 수 없다. 리비전 a3c9e8f1b274 는 아무도 자동 승격하지 않는다
12 KST→UTC 리비전 e5a7c2d9f310 적용 전 백업, 기존 값의 시간대가 +09:00 이 아니면 LEGACY_OFFSET 수정 모든 시각이 오프셋 차이만큼 어긋난 채 저장된다(§10)
13 /admin 은 슈퍼유저 로그인이 필요하다 — 세션은 Redis 서버 세션, SESSION_SECRET_KEY 는 세션 ID → Redis 키 HMAC 키. ADMIN_SESSION_MAX_AGE_SECONDS(절대)·ADMIN_SESSION_IDLE_SECONDS(미사용)를 정책에 맞춘다(README 세션·토큰 만료) 키를 바꾸면 모든 관리 세션이 끊긴다(다시 로그인). Redis 를 읽을 수 있는 사람은 세션 내용(사용자 id·CSRF 토큰)을 본다 — Redis 접근을 통제한다 (쿠키는 HMAC 때문에 Redis 키로 만들 수 없다, admin-session-hardening R-008)
14 ACCESS_LOG_RETENTION_DAYS 를 개인정보 정책에 맞추고(기본 365일), Celery worker 와 beat 한 개를 띄운다 beat 가 없으면 보존 삭제가 돌지 않아 접속 로그가 무기한 쌓인다(§6·§9)

11.2 배포 절차와 확인

uv run alembic current            # 현재 리비전
uv run alembic upgrade head       # writer 에서 적용 (ALEMBIC_DATABASE_URL 로 DSN 분리 가능)
# 되돌리기: uv run alembic downgrade -1  (MySQL CI job 이 downgrade -1 → 재-upgrade 를 검증한다)

배포 후:

curl -s https://<host>/health                                            # 200
curl -s -o /dev/null -w '%{http_code}\n' https://<host>/ready            # 200 (DB 준비), 아니면 503
curl -s -o /dev/null -w '%{http_code}\n' https://<host>/docs             # DEBUG=false 면 404
curl -s -o /dev/null -w '%{http_code}\n' https://<host>/admin/           # 302(로그인 화면으로), ADMIN_DISABLED=true 면 404

API 와 worker 의 코드·환경 버전을 맞춘다. 무중단 migration 순서·백업/복구 시험은 배포 인프라에서 별도로 승인한다(이 저장소는 이미지 빌드·배포를 다루지 않는다).

11.3 알려진 제한 (구현되지 않은 것)

전제로 삼지 않는다.

  • API 인가의 세분: 슈퍼유저/일반 2단계뿐이다(역할·권한 테이블 없음). Principal 은 토큰 claims 로 만들므로 강등·비활성화는 refresh 폐기로 다음 회전부터 막히고, 이미 발급된 access 는 만료까지 이전 권한을 가진다.
  • 관리 화면 인증의 범위: 슈퍼유저 한 등급만 들어간다(관리 화면 안의 세분 권한 없음). 상태를 바꾸는 관리 요청은 모두 CSRF 토큰을 요구하지만 sqladmin 사용자 정의 @action(GET 라우트)은 보호 밖이다 — 이 저장소는 쓰지 않는다(admin-session-hardening R-001). 관리 화면과 API 는 같은 판정(revocation_for_change)으로 같은 집합을 커밋 전에 폐기한다(R-007 해소). 같은 경로를 메서드별 라우트로 나눈 경우 405 의 Allow 가 불완전하다 (사용자 결정으로 현행 유지, R-002). 익명 로그인 화면 방문도 Redis 세션(미사용 30분)을 만든다(R-003).
  • access 토큰 즉시 폐기: 블랙리스트 없음 — 짧은 수명(15분)과 refresh 폐기(logout·재사용 탐지·비활성화·강등·비밀번호 변경·삭제)로 대신한다.
  • 접속 로그 신뢰 경계: ip_address 는 TRUSTED_PROXY_HOPS 가 실제 프록시 홉 수와 같을 때만 정확하다 — 값이 실제보다 크면 위조된 XFF 값을 믿는다. forwarded_for·real_ip 열은 헤더 원문이라 위조될 수 있다. Referer·User-Agent·session_id 쿠키 원문과 (민감 키를 가린) query string 이 저장된다 (사용자 결정). 보존 기간은 ACCESS_LOG_RETENTION_DAYS(기본 365일)이고 beat 가 떠 있어야 삭제된다(§6). 개인정보 정책을 배포 측에서 정한다.
  • 접속 로그 내구성: best-effort(상한 초과 drop, 종료 drain 5초). drop 과 drain timeout 로그를 모니터링한다.
  • 레이트 리밋: 인증 엔드포인트(로그인·가입)에만 있다(§7). 그 밖의 요청 한도는 리버스 프록시나 API gateway 에서 건다.
  • 자동 앱 탐색: 없음(설계 원칙).
  • 미사용 설정: 없다. 메일·업로드 설정과 SESSION_EXPIRE_SECONDS(config-cleanup), API 버전 설정(config-cleanup-2)은 지웠다(.env 에 남아도 무시된다). 로그 포맷·콘솔 스위치는 로깅 구성에 연결했다(§5). 새 설정이 읽히지 않으면 tests/core/test_settings_contract.py 가 막는다.
  • 검증하지 않은 것: Raw 집계의 실행 계획·실제 replica 지연·부하 한계(운영급 데이터 필요), 실제 배포 플랫폼의 secret store·TLS·프록시 ACL.
